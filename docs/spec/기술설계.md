# 기술 설계 — 통합 범위 구현 계획

개정일: 2026-11-14
기준: [서비스 기획서](서비스기획서.md). 2026-11-14 개정으로 이전 1차·2차를 하나의 범위로 합쳤다(홈서버·로컬 LLM, 공개 배포 없음). 아래에서 '1차'라고 남은 표현은 이미 구현·검증한 기반 부분을 가리키며, G절은 통합 범위에서 새로 붙이는 확장 설계다.

## A. 구조와 생략할 구성

`브라우저 —Tailscale 사설망→ 홈서버[웹·단일 서비스 API·작업자·SQLite·비공개 파일·로컬 LLM(Ollama, 127.0.0.1)]`

홈서버 한 대에 웹·API·작업자 한 개·서버 예약 실행·로컬 LLM을 둔다(사용자 결정 2026-11-14). 홈서버 장비: Intel i7-6700HQ 4코어, RAM 8GB(싱글 채널, 증설 안 함), SSD 128GB·HDD 1TB, Ubuntu 설치 예정. LLM용 GPU는 설치 후 확인한다. 메일·공고·서류 추출은 화면 요청과 분리해 작업 기록을 남기고 처리한다. Redis·전용 메시지 브로커·여러 마이크로서비스·실시간 WebSocket은 1차 필수로 도입하지 않는다.

- 클라이언트는 작업 ID로 상태를 확인한다. 처리중일 때만 제한적으로 조회하고 완료 후 멈춘다. 앱 재실행 시 최근 작업 결과를 읽는다.
- DB에 대기·실행중·성공·일부 실패·실패를 기록한다. 사용자/연결/작업 종류별 중복을 합치고 작업 중 서버가 중단되면 재시도할 수 있어야 한다.
- 작업은 원자적으로 선점하고 실행 만료 시각을 둔다. 재시작 후 남은 실행중 작업을 복구하되 같은 이벤트를 두 번 반영하지 않는다. 작업자 한 개여도 내구성·중복 방지를 생략하지 않는다.
- 서버 예약은 하루 한 번을 초기값으로 한다. 정확한 시각은 배포 설정, 21시는 후보. 수동 요청과 같은 처리 경로를 사용한다.
- 구현(P1-06): 서버 프로세스의 예약 검사기가 1분마다 한국 시간 기준 `NEXTSTEP_SCHEDULE_HOUR`(기본 21시) 이후 `초대 테스트 권한 AND 자동 ON` 사용자에게 이력서·프로필이 있으면 갱신, 메일 연결이 정상이면 메일 작업을 만든다. 사용자·날짜·종류별 한 번만 만들고(재시작해도 중복 없음) 같은 종류 대기 작업이 있으면 재사용한다. 자동 OFF·연결 해제 시 대기 작업을 지우고 실행 중 작업은 마친다. 설정 화면은 최근 예약 실행 결과를 보여 준다.
- 자동화 조건은 `자동화 권한 유효 AND 자동 ON AND 필요한 연결 정상`이다. 권한 공급원은 초대 테스트 권한이며 구독은 두지 않는다(2026-11-10).
- 자동 작업 등록·실행·반영에서 권한을 확인한다. OFF·연결 해제 시 새 예약은 중단하고 진행 작업은 안전하게 중단·대기로 정리한다. 사용자의 명시적 수동 요청과 구분한다.
- 앱 종료·컴퓨터 꺼짐은 서버 중단 조건이 아니다. 모든 처리 작업을 클라이언트 타이머로 구현하는 방식을 사용하지 않는다.

개발은 운영자 Mac에서 하고 원격 저장소에 올린 코드를 홈서버가 받아 `pnpm install --frozen-lockfile`·`pnpm build` 후 웹·API를 서비스로 재시작한다(사용자 결정 2026-11-14). DB는 홈서버의 SQLite를 유지한다. 원본 파일은 비공개 저장소, 연결 비밀정보는 별도 암호화·접근 통제 경로로 관리한다. 공개 배포는 하지 않는다.

### 로컬 LLM 실행

- Ollama를 홈서버에서 `127.0.0.1`에만 열고 API 서버만 호출한다. 11434 포트는 인증이 없으므로 사설망에도 열지 않는다.
- 모델 후보는 Qwen3 4B(Q4_K_M, 약 2.5GB), 대안 Gemma 3 4B. 설치 시점에 3~4B급 최신 모델을 다시 확인하고 정답 사례로 측정해 고른다. 7~8B는 RAM 8GB 싱글 채널에서 느리고 빠듯해 쓰지 않는다.
- 메모리 예산: OS 약 1GB, 웹·API 약 0.6GB, Ollama+4B 모델 약 3~3.5GB. 동시 처리 1개, 문맥 4,096 토큰, 작업이 끝나면 모델을 메모리에서 내린다. Qwen3의 생각 모드는 끈다.
- 출력은 JSON Schema 구조화 출력으로 받고 공통 계약 schema로 다시 검증한다. 형식이 틀리면 한 번 재시도하고 그래도 틀리면 해당 항목을 미확인으로 둔다.
- 처리 속도는 공고 1건 추출 약 1분으로 추정한다(실측 전). 작업마다 하루 처리 상한을 두고 남은 건은 다음 실행으로 넘기며, 처리 중 건수와 남은 예상 시간을 작업 결과에 남긴다.

## B. 최소 데이터 모델과 지금 필요한 확장 지점

아래는 개념 객체이며 객체 하나마다 서비스·별도 화면·복잡한 테이블 체계를 만들라는 요구가 아니다. 조회·정합성에 따라 관련 필드를 묶되 사용자 경계와 근거는 유지한다.

| 객체 | 저장할 내용 | 확장 시 유의점 |
|---|---|---|
| 사용자·권한 | 사용자 ID·인증 주체·초대 자동화 권한·자동 ON/OFF | 공개 가입·구독은 두지 않음. 사용자별 AI 키·모델은 제거(2026-11-14) |
| 메일 연결·위치 | 사용자·provider·제공자 계정 ID·비밀정보 참조·연결 상태·편지함별 확보 위치 | 다른 제공자를 더하면 provider별 위치를 따로 둔다. 네이버 위치를 재사용하지 않음 |
| 활성 문서 | 사용자·kind(resume·portfolio·career)·원본 키·변환 방식(텍스트·ZIP·OCR)·변환된 MD(사용자 수정 가능)·확인 사실·교체 시각 | kind별 한 개. 다른 kind 교체가 이력서를 덮어쓰지 않음 |
| 프로필·필터 | 확인된 직무·경력·지역·고용형태·기술·갱신 식별 | 새 직군·조건을 추가. 원본 사실과 추정 구분 |
| 공고·출처 | 내부 공고 ID·출처 ID·출처별 공고 ID/URL·로컬 LLM이 뽑은 구조화 사실과 추출 버전·마감·확인 시각·확인 가능한 기업 유형/규모와 근거 | 새 수집기를 같은 구조로 정규화. 회사명만으로 통합 금지 |
| 추천·숨김 | 사용자·공고·기준 프로필/문서 식별·근거·후보 분류·숨김 | 선호·상세 피드백 추가. 과거 추천을 새 기준으로 위장하지 않음 |
| 지원 | 내부 ID·사용자·회사·직무·회차·선택 공고 참조·개인 상태·열람·수동 관리 | URL은 기본키가 아님. 새 출처·조회와 무관하게 유지 |
| 메시지·이벤트·정정 | provider/계정/메시지 ID·최소 근거·발생/수신 시각·대상·결과·정정 이력·재적용 억제 | 제공자 간 중복은 보조 식별로 대조. 원본 ID는 보존 |
| 확인 요청 | 연결 불명·모호·최종 결과 충돌·근거·선택 대상·처리/무시 | 보류·잠금·고급 비교 UI 추가. 기존 처리 결과 보존 |
| 작업·결과·최소 이벤트 | 작업 ID·소유자·종류·멱등 키·상태·시도·최근 성공·오류 코드·건수 | 별도 큐·운영 분석 도입 시 작업 ID·결과 계약 유지 |

provider·문서 kind·출처 ID를 문자열/명시 코드로 다루고 두 번째 연결 시 기존 ID 의미가 바뀌지 않게 한다. 아직 없는 기능을 위해 범용 플러그인 프레임워크·전 직군 대형 분류 체계·결제 테이블을 미리 구현하지 않는다.

## C. 메일 조회·판정·정정

### 연결과 증분 처리

- 네이버 한 계정, IMAP 설정·앱 비밀번호·TLS·읽기 전용 조회. 기존 개인 키체인을 신규 사용자 인증 저장소로 사용하지 않는다.
- 최초 조회 기간은 연결할 때 1·3·6·12개월 중 고르고 동의받는다(기본 3개월, 조회 범위 시작 `covered_since`). 구현(P1-12, 2026-11-14): 과거 범위 넓히기는 3·6·12·24개월까지 고르면 현재 조회 위치(커서)를 바꾸지 않고 [목표 시작, 조회 범위 시작) 기간을 최근 것부터 편지함별 실행당 300건씩 가져오고(`mail_backfill` 진행 위치), 다 가져오면 조회 범위 시작을 목표로 옮긴다. 예약 실행은 자동 ON 사용자에게 메일 작업을 매시간, 공고 갱신을 하루 한 번 만들고 30일 지난 예약 기록을 지운다.
- 구현(P1-05 기반): 연결 정보는 사용자당 하나이며 비밀번호는 DB와 다른 키로 암호화한다. 작업자는 편지함별 UIDVALIDITY·마지막 UID 이후만 조회하고(실행당 편지함별 300건, 남으면 다음 실행), 메일 처리를 저장한 뒤 위치를 전진시킨다. 메시지 키(Message-ID, 없으면 편지함·UIDVALIDITY·UID)로 중복을 막는다. 저장 근거는 수신 시각·제목 앞 80자·짧은 발췌·공고 키다. 공고 키로 지원 건이 하나만 맞으면 순서(미지원<지원 완료<전형 진행중<최종 결과)를 거스르지 않을 때만 반영하고, 최종 결과 충돌·모호는 확인 요청을 만든다. 공고 키가 수집 공고와 맞으면 지원 건을 만들고 지원일은 만들지 않는다. 식별하지 못한 메일은 `unlinked`로 보관하고 편지함·UIDVALIDITY·UID만 남긴다. AI가 설정되면 같은 작업에서 본문(이번 실행분은 메모리, 이전 보관분은 읽기 전용 재조회)을 AI로 해석해(현재 코드는 OpenAI, 통합 범위에서는 홈서버 로컬 LLM이 회사·직무·결과를 추출하고 반영 규칙은 그대로 둔다) 채용 무관이면 제외, 회사·직무·결과가 명확(high)하고 같은 회사·직무 지원 건이 하나면 반영, 없으면 지원 건 생성(지원일 미생성), 같은 회사 다른 직무·확신 낮음·모호면 확인 요청으로 넘긴다. 실행당 60건, 메일당 3회까지 시도한다. 무시·연결 해제 시 삭제한 근거는 억제 목록에 남긴다.
- 실제 계정 검증(2026-11-07): 3회 증분 실행에서 채용 메일 542건 저장, 중복 0건, 확보 위치 전진, 합격 판정은 안내 문구 오판을 막은 뒤 6건.
- 네이버 IMAP 노출 상한은 계정 설정 "IMAP 동기화 메일 제한"(환경설정 > POP3/IMAP 설정 > IMAP/SMTP 설정, 기본 1,000통, 선택 1,000~5,000통, 무제한 없음)이다(2026-11-07 확인). 계정당 최대 5,000통을 전제로 하고, 범위 미달이면 설정 위치를 안내한다.
- 네이버 받은편지함은 P1-01에서 정확히 1000건만 노출됐다. 최초 조회는 편지함에 노출된 가장 오래된 메일이 조회 시작일보다 늦으면 범위 미달을 사용자에게 표시하고 완료로 보고하지 않는다.
- 수신·분류 폴더를 포함하고 프로모션 등에 있는 결과 메일 누락을 점검한다. 보낸·임시·휴지통·스팸은 기본 조회에서 제외하고 조회 범위를 명시한다. 스팸 포함 선택은 기간 선택과 함께 제공한다.
- 편지함별 UIDVALIDITY·확보 UID를 기록한다. P1-01에서 네이버 받은편지함이 RFC와 달리 UIDVALIDITY 0을 반환했으므로 UIDVALIDITY만으로 초기화를 판정하지 않고 메시지 ID 대조를 함께 쓴다. 수집 자료·처리 작업을 내구성 있게 확보한 뒤 위치를 전진시킨다. 분류·반영 실패는 별도 재시도한다.
- UID 초기화·편지함 이동·재연결을 범위 재검증과 메시지 식별로 복구한다. 일부 폴더 실패 시 실패 위치는 유지하며 다른 결과는 부분 완료로 표시한다.
- 버튼 클릭 시각은 동기화 기준이 아니다. 같은 메일을 여러 번 확보해도 상태·지원·확인 요청을 중복 생성하지 않는다.

공식 근거: [네이버 IMAP 안내](https://help.naver.com/service/30029/contents/21349?lang=ko&osType=PC).

### 공통 처리

`수집 → 채용 여부 → 회사·직무·식별자 → 지원 연결 → 결과 해석 → 최신성·정정 확인 → 반영/확인 요청`

- 템플릿·명시 사실·필요한 모델 해석을 조합하되 AI가 자의적으로 대상을 선택하지 못하게 한다. 모델은 홈서버 로컬 LLM이며 메일 본문이 홈서버 밖으로 나가지 않음을 안내한다.
- 회사명만 같거나 후보가 하나뿐이라는 이유로 연결하지 않는다. 접수 ID·URL·직무·회차·시간 관계로 확인한다.
- URL 없는 결과·접수 없는 결과를 지원하며 지원일은 임의 생성하지 않는다. 회사 없는 메일·홍보는 제외한다.
- 문서·메일·공고 안의 명령은 입력 자료로만 취급한다. 인증정보 접근·서비스 정책·도구 실행 지시로 사용하지 않는다.
- 상태·개인 결과·공고 마감은 분리한다. 오래된 접수/열람은 최신 상태를 되돌리지 않는다.
- 수동 등록·진행 확인은 영구 잠금이 아니다. 잘못된 근거/연결은 해당 조합의 재적용만 막고 독립적인 새 근거는 평가한다. 최종 결과 충돌·최신성 불명은 확인 요청한다.
- 반영 직전 현재 상태·정정·근거를 트랜잭션에서 재확인한다. 수동 수정과 작업 경합을 검증한다.
- 정정·무시한 같은 근거는 재요청하지 않는다. 단순 메일 근거 대기는 확인 요청을 생성하지 않는다.

상태·연결·제외·모호·충돌의 정답표를 먼저 만든다. 합성·비식별 표본을 우선하며 실제 사용자 원문은 동의 범위를 벗어나 시험 데이터로 수집하지 않는다.

## D. 공고·추천·문서

### 출처 검증

사람인·잡코리아·자소설닷컴·원티드·점핏 다섯 곳을 출처로 두고(2026-11-14 통합. 캐치·고용24는 제거 유지) 공개 목록/상세·직무·마감·원문·실제 지원 URL·조회 실패 구분을 각각 확인한다. 수집 가능성이 검증되지 않으면 구현 완료로 표시하지 않는다. 제약이 발생하면 보고하고 범위 변경을 별도 결정하며 다른 출처로 임의 교체하지 않는다. 다섯 출처의 실제 추천 흐름은 완료 조건이다.

잡코리아 상세 페이지의 hydration 데이터에서 마감·상시채용·경력·접수 방식·홈페이지 지원 URL·명시된 기업 유형/직원 수를 얻는다. 본문이 이미지뿐인 공고는 본문 실패로 표시하고 텍스트로 추정하지 않는다. 직원 수 0은 미확인이다. 검색어 목록에는 다른 직무가 섞이므로(예: `서비스 기획` 검색에 영업직) 추천 수집에는 출처의 직무 분류 필터가 필요하며 P1-04에서 검증한다.

원티드(개인회원 약관 제19조 7항)·자소설닷컴(이용약관 제14조 9호)은 사전 허락 없는 자동 수집을 금지하고 원티드 OpenAPI는 개인 발급이 불가하다. 세 출처 모두 얻은 정보의 사전 동의 없는 제3자 제공을 금지한다. 채용공고 크롤링을 데이터베이스제작자 권리 침해로 본 판례(서울고법 2016나2019365)가 있다. 사용자는 공개 서비스를 하지 않고 운영자와 초대 사용자만 쓰는 무료 서버로 운영하기로 하고 이 위험을 인지해 세 출처 자동 수집을 결정했다(2026-11-10). 위험을 줄이려고 공고는 갱신을 요청한 사용자 자료로만 저장하고 다른 사용자와 공유하지 않는다. 이전의 서비스·개인 수집 모드 구분과 `SOURCE_POLICY`는 제거했다. 원티드 OpenAPI 담당자는 제휴 문의 회신(2026-11-10)에서 기업고객이 아니라 발급이 어렵다고 했고, 크롤링이 아니어도 복사·복제는 약관 제19조의 어뷰징일 수 있다는 의견과 고용정보원 OpenAPI를 안내했다. 사용자는 이를 알고 원티드 자동 수집을 유지하기로 했다(2026-11-10). 조건: 운영자와 초대 사용자만 쓰고 하루 한 번·요청 간격을 지키며, 차단되면 우회하지 않고 멈추고, 원티드의 정식 중단 요청이 오면 원티드를 사용자가 넣은 링크 판정만으로 바꾼다. 고용24 채용정보 OpenAPI는 기업회원 전용·공공누리 제4유형이다(2026-11-07 조사). 외부 문의·허가 요청은 사람인 OpenAPI 하나만 진행하고 다른 출처는 회신을 기다리지 않는다(사용자 결정 2026-11-10, 배포해 사용자를 모으지 않는다는 전제). 같은 날 1차 출처를 사람인·잡코리아·자소설닷컴으로 바꿨다. 사람인은 OpenAPI가 승인되면 API(본문 필드가 없어 판정 근거는 상세 공개 페이지 보강 필요, "Powered by 취업 사람인" 표기)로, 거절·대기 중이면 같은 조건의 공개 페이지 자동 수집으로 가져온다. 원티드 수집기는 구현돼 있고 2026-11-11 자동 수집 목록에서 뺐으나, 통합 범위(2026-11-14)에서 같은 조건으로 다시 자동 수집한다. 점핏(사람인 약관 적용)도 같은 조건의 자동 수집으로 붙인다. 캐치(이용약관 v2.4 제19조⑤ 10·11호 크롤링 명시 금지)·고용24는 출처 후보에서 제거했다.

- 로그인하지 않고, 403·429를 받으면 그 호스트 요청을 멈추며 IP 변경·캡차 우회를 하지 않는다.
- 목록 확보: 원티드는 목록 HTML에 공고 링크가 없어 웹 화면이 쓰는 공개 목록 JSON을 직무 태그로 조회하고, 자소설닷컴은 웹 화면이 쓰는 공개 직무별 목록(직무 분류 ID: 프론트엔드 175·웹 162, 앱 161·172·173, UI·UX 241, 서비스기획·PM 171)을 쓴다. sitemap은 직무 정보가 없어 대상 공고를 찾지 못했다. 상세는 두 출처 모두 공개 페이지의 `__NEXT_DATA__`를 읽는다. 제목이 교육생·수강생·훈련생·부트캠프·클래스메이트·국비 교육·'N기 모집'인 공고는 채용이 아니므로 저장·판정하지 않고 건수만 결과에 남긴다. 작업 결과의 AI 실패는 원인 코드별 건수(`aiFailureCodes`)로 남긴다.
- 원티드 상세에는 기업 유형·규모가 없어 미확인이다. 자소설닷컴 본문은 대부분 이미지라 현재는 모집 분야 문구로만 판정하고 본문은 미확인으로 둔다. 공고 이미지 OCR은 홈서버 CPU 부담을 측정한 뒤 정한다(서류 OCR과 별개).
- 메일 알림에서 공고를 얻는 방식은 후보를 플랫폼이 정하고 본문이 없어 이력서 대조가 불가능해 채택하지 않았다.

선정 이유는 사용자 요구에 따른 공고 탐색 범위 확보 및 스타트업·기업 규모 비교다. 기업 유형/규모는 해당 공고·기업 소개의 명시 사실과 근거가 있을 때만 저장·표시한다. 정보 없음은 미확인으로 두고 플랫폼 이름만으로 스타트업·대기업을 추정하지 않는다. 별도 기업정보 크롤러·추정 모델은 추가하지 않는다.

출처별 공고를 사용자별로 저장하고(`postings.owner_user_id`, 같은 공고도 사용자마다 따로) 사용자 필터로 추천한다. `acquired_by`는 자동 수집(auto)과 사용자 링크(link)를 구분한다. DB 버전 10에서 이전 공용 공고와 그 추천을 지웠다. 목록 수집·추천 재계산·모집 상태 확인을 구분한다. 필터 변경은 기존 데이터로 먼저 계산하고 재수집 여부·확인 시각을 표시한다. 공고 마감 재확인은 정기 수집과 명시적 새로 가져오기에 포함한다. 지원 직전 강제 재조회·출처별 요일 최적화는 두지 않는다.

### 추천과 추출

- 판정 구조(사용자 결정 2026-11-14, 2026-11-14 구현): 모델은 정보 추출만 한다(`prompts/requirements.ts` 공고, `prompts/candidate.ts` 지원자, 분류는 `recommend/classify.ts`). 이 구조는 구현 기간의 OpenAI에도 먼저 적용해 공고당 호출을 추출 1회로 줄이고(판정 호출 제거), 마지막에 모델만 로컬 LLM으로 바꾼다. 공고에서 직무군·필수/우대 조건·요구 연차·고용 형태·원격·포트폴리오 필수 여부를 사용자별 공고마다 한 번 뽑는다(추출 버전이 같으면 그 사용자 안에서 재사용). 추출 결과는 사용자 간에 공유하지 않는다(사용자 결정 2026-11-14, 사용자별 자료 원칙 유지). 따라서 AI 호출 수와 홈서버 부하는 사용자 수에 비례하며 하루 처리 상한을 사용자별로 나눠 배정한다, 서류에서 보유 기술·직무별 연차·역할 경험을 서류가 바뀔 때만 뽑는다. 분류(제외 > 도전 > 미확인 > 기본)와 근거는 아래 초기 판정 규칙을 코드로 적용한다. 로컬 LLM 호출 전에 출처 목록·상세의 사실(지역·경력 상한·고용 형태·교육 모집)로 먼저 거르고 통과한 공고만 추출한다. 추출 결과가 불확실하면 그 조건은 미확인이다. '다른 성격의 필수 경력' 같은 의미 판단은 추출 단계에서 공고 조건과 서류 경험의 직무 성격을 함께 뽑아 규칙으로 비교하며, 정답 사례로 측정한다. 기준은 54/57(기획서 3절).
- OpenAI 최소 사용 원칙(구현 기간): 사전 필터를 통과한 새 공고만 추출하고 그 사용자의 같은 공고는 추출 버전이 같으면 재사용한다. 판정 호출은 두지 않는다. 개발 중 반복 실행은 `NEXTSTEP_AI_CACHE_DIR`로 같은 입력의 응답을 재사용한다. 정답 사례 재평가는 판정 구조를 바꿀 때만 한다.
- 현재 구현(P1-08, 로컬 전환 시 제거): AI 처리는 사용자 본인 OpenAI 키·선택 모델로만 한다. 키는 등록 시 OpenAI 모델 조회(요금 없음)로 키·모델 권한을 확인하고 연결 비밀정보와 같은 키로 암호화해 사용자별로 저장한다. 작업자·요청은 사용자 범위에서 그 키를 쓰며, 키가 없으면 AI 단계를 미설정 실패로 남기고 메일 해석은 건너뛰어 재시도 횟수를 쓰지 않는다. 실패는 키 거부·잔액 부족·모델 불가·기타로 구분해 화면에 표시한다. 모델 목록은 정답 사례로 정확도를 잰 gpt-5.5·gpt-5.4-mini만 둔다. 로컬 LLM 경로가 측정 기준을 넘는 변경에서 이 기능(`ai_settings`·키 확인·설정 화면)을 제거한다.
- 구현(P1-04): 갱신은 사용자별 작업(대기·실행중·성공·일부 실패·실패)으로 처리한다. 작업자는 세 출처에서 직무별 소량(출처별 직무당 5건)을 그 사용자 자료로 모으고, 공고 원문은 AI 조건 추출(직무군·필수·우대·원격·포트폴리오 필수)에만 쓰고 추출 결과만 저장한다. 판정은 갱신마다 서류에서 지원자 사실을 한 번 추출하고(사용자가 확인한 프로필 직무 경력이 있으면 그 기간 우선) 저장된 공고 사실과 규칙으로 분류한다. 프로필 저장 시각·이력서 ID·추출 지시·규칙 버전이 같으면 다시 분류하지 않고 지원자 추출도 하지 않는다. 이전 형식으로 추출된 공고는 다시 수집될 때까지 본문 조건 미확인으로 둔다. 사용자가 넣은 링크로 가져온 공고는 그 사용자 전용이다. 선호 필터는 출처가 받는 조건이면 수집 요청에 넣고(원티드: 시·도 지역·연차 범위, 잡코리아: 경력 범위·정규직. 2026-11-08 실제 확인), 받지 않는 조건(잡코리아 지역, 자소설닷컴 전체)은 목록을 최대 세 배까지 보며 상세의 근무지·경력으로 거른다. 고용 형태는 본문 조건 추출 결과로 판정 전에 거른다. 근무지·경력·고용 형태가 미기재면 통과시켜 판정에서 미확인으로 둔다. 필터를 바꾸면 다시 가져오기 전에도 기존 추천을 현재 필터로 거르고, 사용자가 넣은 링크 공고는 거르지 않는다. 원격 포함을 고르면 원티드 지역 조건을 걸지 않는다(서울 밖 전면 원격 공고 보존).

- 프론트엔드·앱 개발·디자인·기획의 확인된 조건·경력·업무·도구·경험을 기준으로 기본/도전/미확인 분류와 근거를 제공한다. 앱 개발에는 iOS·Android·크로스플랫폼을 포함한다. 필수·우대·미기재를 구분한다.
- 복수 직무는 OR, 다른 필수 조건 그룹은 AND. 동의어와 유사 경험으로 명시적 필수 경력을 위조하지 않는다.
- 정답 사례(`apps/server/tests/prompts/recommendation-cases.json`)가 정한 초기 판정 규칙: 제외 > 도전 > 미확인 > 기본 순으로 우선한다. 같은 직무 연차 부족은 폭과 무관하게 도전, 다른 성격의 필수 경력(예: UX 리서치·PO 직책·특정 기술 실무)은 유사 경험으로 대체하지 않고 제외한다. 이력서에 없는 단순 필수 기술·포트폴리오 필수·역할 수준(리딩)은 미확인이다. 서울 밖 사무실은 전면 원격일 때만 기본, 근무지 미기재는 미확인, 마감은 기준 시각으로 비교해 지나면 제외한다. 디자인은 UI/UX·프로덕트 디자인, 기획은 서비스 기획·PM/PO만 대상이며 공간·패션 디자인, 사업·상품·영업기획은 제외한다. 사용자가 확정했다(2026-11-07).
- 초기 추천 규칙과 정답 사례를 프론트엔드·앱 개발·디자인·기획 각각에서 확인한다. 디자인·기획은 개발 기술 중심 규칙을 그대로 적용하지 않고 해당 업무·도구·경험을 평가한다. 백엔드·QA는 통합 범위이며 직군별 정답 사례를 먼저 만든다(마케팅은 2026-11-14 제외). QA는 테스트 설계·자동화 도구·품질 업무 경험으로 평가한다. 전 직군 분류·개인화 점수 최적화는 두지 않는다.
- 이력서(필수)·포트폴리오·경력기술서(선택) kind별 한 개. 텍스트 PDF·MD·Notion ZIP·스캔 PDF를 모두 MD로 변환해 저장하고 분석은 MD로만 한다. 이미지가 있는 쪽은 OCR로 MD를 만든다. 변환된 MD·경력·기술은 사용자가 확인·수정한다(사용자 결정 2026-11-14). 판정 입력은 kind별 추출 결과를 합친 구조화 사실이며 이력서 앞부분 글자 수 제한에 기대지 않는다. PDF/MD 파일당 20MB를 초기값으로 사용한다.
- 업로드는 서버 크기·유형·처리 시간 제한을 적용한다. 암호화·손상·스캔 PDF 미지원은 실패로 표시하고 텍스트 PDF/MD 등록을 안내한다. 일부 쪽만 글자가 없는 PDF는 등록하되 그 쪽 번호를 저장해 추천에 쓰이지 않는다고 경고한다. 실행 파일·임의 경로 접근을 허용하지 않는다.
- 새 문서 확인 성공 후 대표를 교체하고 기존 원본·본문을 삭제한다. 실패·취소 시 기존 대표를 유지한다. 삭제된 구 문서 ID는 추천 기준 식별용 최소 메타데이터만 남긴다.

## E. 웹·보호·홈서버

완료 조건은 웹 브라우저 기준이다. Electron 데스크톱 앱은 제거했다(사용자 결정 2026-11-14, P1-14). 웹과 API는 홈서버에서 실행하고 Tailscale 사설망으로만 접속하게 해 인터넷에 직접 노출하지 않는다. 홈서버는 재부팅 후 웹·API·작업자·Ollama를 자동 시작한다.

- 초대 사용자는 Tailscale 계정을 만들고 운영자가 홈서버 기기를 공유해 접속한다. 초대 링크 주소(`NEXTSTEP_WEB_URL`)는 사설망 주소로 지정한다.
- 사설망 접속은 HTTPS로 한다(사용자 결정 2026-11-14). Tailscale MagicDNS 주소와 Tailscale HTTPS 인증서(`tailscale cert` 또는 `tailscale serve`)를 쓰고 세션 쿠키에 secure 속성을 켠다. 초대 링크 주소도 이 HTTPS 주소다. 인증서 갱신은 운영 점검 항목에 넣는다.
- 원문·지원 페이지는 URL·스킴을 검사해 새 창으로 연다. 브라우저·사용자 컴퓨터를 끈 동안의 처리는 홈서버 작업자가 한다.
- 접속 재개·세션 만료·네트워크 복구 시 현재 서버 결과를 조회한다. 오프라인 편집은 제공하지 않고 연결 안내·재시도를 제공한다.
- 홈서버 코드 갱신은 운영자가 수동으로 한다(git 받기·빌드·서비스 재시작). 업데이트 주체·버전은 관리하고 취약한 의존성을 방치하지 않는다.
- 백업(DB·`files/`·`secret.key`)은 홈서버 노트북 밖(운영자 Mac·외장 디스크 등)에 두고 다른 위치 복구를 연습한다. 같은 노트북의 HDD만으로는 백업으로 보지 않는다. `secret.key`는 DB 백업과 따로 보관한다.

### 보호·삭제는 필수

- 개인 데이터는 모두 사용자 소유·접근 범위를 강제하고 비공개 파일 URL·다운로드 권한을 검사한다. 다른 사용자 ID를 보내도 접근할 수 없어야 한다.
- 원본·추출문·메일과 인증정보는 DB/파일/비밀정보 저장 경계를 나눈다. renderer 저장소·로그·프로젝트 파일에 평문 자격정보나 메일 원문을 남기지 않는다.
- 연결 해제는 조회 중단·비밀정보 삭제, 기존 지원은 유지/삭제 선택. 지원 삭제 시 같은 과거 근거로 재생성되지 않도록 최소 억제 식별을 둔다. 계정 삭제 시 사용자 근거·파일·억제 식별까지 삭제한다.
- 작업 취소·삭제와 실행이 겹쳐도 삭제한 개인 정보·지원이 작업 종료로 되살아나지 않아야 한다.

## G. 통합 범위 확장 설계와 재작업 방지

### 입력 범위 확대

- Gmail은 일단 범위에서 뺐다(2026-11-14). 다시 넣으면 네이버 구현을 복제하지 않고 별도 제공자 수집기·인증·위치로 추가한다.
- 원티드·점핏은 출처별 추출·마감·지원 URL 검증 뒤 공통 공고로 변환한다. 구현(2026-11-14): 원티드는 기존 수집기를 자동 수집에 다시 넣고, 점핏은 웹 화면이 쓰는 공개 JSON API의 직무 분류별 목록·상세를 읽는다. 점핏 공고 ID는 사람인 공고 번호와 같아 한 사용자에게 같은 번호의 사람인·점핏 공고는 먼저 저장된 하나만 둔다. 점핏은 개발 직무(프론트엔드·앱 개발·백엔드·QA)를 고른 경우에만 조회하며(2026-11-14) 출처 간 통합은 확인 가능한 동일 공고에만 적용한다. 출처가 늘면 로컬 LLM 추출 건수가 늘므로 하루 처리 상한 안에서 출처·직무별로 나눠 배정한다.
- 백엔드·QA 등 추가 직무는 필터 선택지만 늘리지 않고 직군별 경력·조건·추천 정답 사례를 추가한다. 기존 네 직무 결과로 새 직무 품질을 보장하지 않는다.

### 문서·추천 확장

- 문서 kind·변환 방식 추가로 포트폴리오·경력기술서·ZIP·OCR을 연결한다. 변환 결과는 모두 MD다. 기존 이력서·추천 이력을 덮어쓰지 않는다. 추가 서류는 미등록이 기본값이다.
- ZIP은 50MB·해제 후 200MB/500파일 초기값과 경로 이탈·압축 폭탄·실행 파일 차단을 실제 지원 전에 구현한다. 미지원 기간에는 ZIP 업로드 자체를 허용하지 않는다.
- 구현(P1-13, 2026-11-14): 추천 목록은 출처·7일 안 마감·제목/회사 검색·정렬(분류·마감 임박·최근 확인)과 분류별 건수를 화면에서 거른다. 피드백(좋아요·별로)과 제외 복구는 `recommendations.feedback·restored`에 두고 다시 판정해도 유지한다. 좋아요는 같은 분류 안에서 위로, 별로는 숨김으로도 처리한다. 지원 건 잠금(`applications.locked_fields`: status·readStatus)은 메일 자동 반영을 막되 모호한 결과의 확인 요청과 사용자의 확인 목록 확정은 그대로 한다. 확인 요청 보류(`review_requests.held`)는 목록 아래로 옮기고 언제든 처리한다. DB 버전 14.
- 고급 필터·선호·피드백은 기존 공고 사실·필수 조건을 보존한 채 추천 계산을 확장한다. 사용자 피드백을 곧바로 회사·직무 전체 차단으로 해석하지 않는다.
- 과거 범위 확장은 별도 작업으로 수행하며 현재 커서를 초기화하지 않는다. 저장된 메시지 ID·정정 억제로 중복·과거 판정 재적용을 막는다.

- 구현(P1-11, 2026-11-14): 서류 API는 `/documents/{resume|portfolio|career}`와 MD 수정 `/documents/{kind}/text`. PDF는 글자 없는 쪽만 200dpi 회색조로 바꿔 OCR(업로드당 40초 상한, 넘친 쪽은 경고), ZIP은 MD 항목만 경로 순으로 합친다. 판정은 이력서·경력기술서·포트폴리오 MD를 합쳐 지원자 사실을 뽑고, 서류를 교체·수정하면 본문 해시가 바뀌어 다시 판정한다.
- OCR은 홈서버 CPU로 서류 업로드 때만 실행하고 처리 시간 제한을 둔다. OCR로 만든 MD는 사용자가 확인·수정한 뒤 추천에 쓴다.

### 자동화·운영 고도화

- 네이버 메일은 1시간 주기 증분 조회를 한다(홈서버 부담 고려, 사용자 결정 2026-11-14). 정기 누락 확인은 보류: 채용과 무관한 메일의 메시지 ID를 저장하지 않아(최소 저장 원칙) 이미 본 메일과 놓친 메일을 구분할 수 없다. 증분은 저장을 마친 뒤에만 위치를 전진시키므로 정상 흐름에서 건너뛰지 않으며, UIDVALIDITY가 바뀐 편지함은 조회 범위 시작부터 다시 본다. provider·계정·편지함별 위치를 분리한다. 메일 AI 해석은 로컬 LLM 하루 처리 상한 안에서 처리한다.
- 단일 작업자를 유지한다. 로컬 LLM 호출은 한 번에 하나이므로 작업 종류(공고·메일·서류)가 모델을 번갈아 쓰도록 우선순위와 상한을 둔다. 작업 종류·멱등 키·기존 ID·권한 검사를 유지한다.
- 명시적 잠금은 별도 설정으로 추가한다. 기존 수동 확인·정정을 전부 잠금으로 마이그레이션하지 않는다. 보류·같은 근거 무시·새 근거 재평가를 구분한다.

### 마이그레이션 원칙

새 필드는 추가·기본값 방식으로 도입하고 원장·사용자·지원·메시지·이벤트 ID를 유지한다. 제공자/문서/출처가 늘어도 과거 자료를 재생성하거나 사용자의 정정을 제거하지 않는다. 호환되지 않는 변경은 데이터 이행·기존 클라이언트 대응·실패 복구를 먼저 확인한다. 아직 착수하지 않은 기능의 스키마를 미리 구현하지 않는다. OpenAI 제거 시 `ai_settings`는 마이그레이션으로 지우고 암호화된 키를 남기지 않는다.

## H. 후속 후보와 공식 참고
