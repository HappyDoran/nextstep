# 맞춤 채용공고 추천·지원 관리 서비스 기획서 v0.2

개정일: 2026-11-04
상태: 기존 결정을 포함해 범위를 재검토한 1·2차 구현 계획. 이번 작업은 문서 정리만 수행하며 앱 코드·서버·계정 연동은 구현하지 않음.
적용 범위: 운영자와 초대 사용자가 쓰는 무료 서비스(2026-11-10 개정). 기존 개인 작업 공간의 Notion·메일·자동화 규칙 및 로컬 현황 생성물과 별개.

## 1. 서비스 방향과 단계 정의

서비스의 장기 방향은 이력서·선택 서류·희망 조건으로 여러 플랫폼의 공고를 추천하고, 사용자가 외부에서 지원한 후 메일과 수동 입력으로 진행 상황을 관리하는 것이다. 대상은 취업·이직 준비자로 유지한다.

- **1차: 비공개 검증용 MVP.** 제한된 계정에서 원티드·잡코리아·자소설닷컴의 프론트엔드·앱 개발·디자인·기획 공고로 추천 → 외부 지원 → 메일 반영 → 모호 확인의 전체 흐름을 실제로 검증한다. 화면 목업이나 수동 관리 전용 앱을 완료로 간주하지 않는다. 1차 완료는 운영자가 NextStep 서버(1차는 로컬 서버, 이후 홈서버)에서 2주 동안 매일 쓰고 초대 지인 1~2명이 써 본 기록으로 판단한다(사용자 결정 2026-11-10). 문제의 근거: 운영자는 이 서비스의 전신인 개인 작업 공간(공고 관리·지원 추적 자동화)을 실제로 써 왔다(사용자 진술 2026-11-10). 전신 사용은 필요성의 근거이며 NextStep 추천 품질의 검증을 대신하지 않는다. 이 프로젝트는 백엔드·홈서버 운영 학습을 함께 목표로 하는 개인 토이 프로젝트다.
- **2차: 초대 기반 확장.** 1차 품질을 확인한 뒤 다섯 플랫폼·두 메일·IT 직무·문서 형식·Windows를 추가한다. 공개 가입·유료 구독은 하지 않는다(사용자 결정 2026-11-10). 확장은 의존 순서대로 나누어 진행하며 한 번에 배포하지 않는다.
- **후속 후보:** 필요성이 검증되지 않은 기능은 2차 필수로 옮겨 적지 않는다. 본인 AI 연결·HWP·Linux·문서 버전 관리·일정 캘린더 등은 별도 재평가한다.

기존 문서의 ‘첫 출시’는 범위가 큰 공개 서비스 목표였다. 이번 개정에서는 최초 검증 제품인 1차와 공개 제공 범위인 2차를 분리한다. 사용자께서 이전에 선택한 항목도 이 기준으로 재배치했다.

플랫폼·직군·형식은 최종 제품 방향에서 삭제하는 것이 아니라 구현 순서를 바꾼다. 비용·가격 산정은 이번 개발 계획의 작업으로 추가하지 않는다.

## 3. 1차 MVP의 사용자·범위

### 제공 조건

- 초대받은 소수의 취업·이직 준비자를 대상으로 비공개 검증한다. 공개 가입·결제·스토어 출시는 하지 않는다.
- 직무 범위는 **프론트엔드·앱 개발·디자인·기획**으로 확정한다. 앱 개발은 iOS·Android·크로스플랫폼 공고를 포함하며 희망 분야는 복수 선택할 수 있다. 백엔드·마케팅은 2차 확장 대상이다.
- 공고 출처는 **원티드·잡코리아·자소설닷컴 세 곳**으로 확정한다. 사용자 선정 이유는 공고 탐색 범위 확보와 스타트업·기업 규모 비교다. 공개 수집 가능성·본문·지원 경로·마감 추출은 각각 검증해야 하며 현재 수집 성공이 입증되었다는 뜻은 아니다.
- 운영 형태(사용자 결정 2026-11-10): 운영자가 운영하는 서버 하나(1차는 로컬 서버, 이후 홈서버)를 운영자와 초대 코드로 가입한 사람만 쓴다. 공개 가입·공개 서비스는 하지 않는다. 저장소를 받아 직접 실행하는 사람은 자기 서버를 스스로 운영한다. 서비스는 전면 무료이며 결제·구독을 만들지 않는다.
- 수집: 세 출처의 공개 페이지를 낮은 속도로 자동 수집한다. 공고는 갱신을 요청한 사용자의 자료로만 저장·판정하고 다른 사용자와 공유하지 않는다. 사용자가 공고 링크 한 건을 넣어 판정할 수도 있다. 로그인·차단 우회를 하지 않는다. 원티드·자소설닷컴은 약관상 사전 허락 없는 자동 수집을 금지하며, 초대 사용자에게 수집 결과를 제공하는 위험을 사용자가 인지하고 결정했다(근거는 기술 설계 부록 D절).
- AI 처리: 사용자가 본인 OpenAI API 키를 등록하고 모델을 선택한다. 요금은 키 주인이 부담한다. 키가 없거나 잘못되었거나 잔액이 없으면 AI 기능을 쓸 수 없다고 원인별로 안내하고, 다른 사용자나 운영자의 키로 대신 처리하지 않는다.
- 확정한 세 출처 중 실제 수집이 불가능한 곳은 제약을 보고하고 범위 변경을 별도로 결정한다. 임의로 사람인 등 다른 출처로 바꾸거나, 실패를 숨기거나, URL 수동 등록만으로 다중 출처 추천 구현을 완료 처리하지 않는다.
- 기업 규모·스타트업 여부는 공고·기업 소개에 명시된 확인 가능한 정보가 있으면 출처와 함께 표시한다. 플랫폼 이름만으로 기업 유형을 단정하지 않고 정보가 없으면 미확인으로 둔다. 별도 기업정보 수집 시스템은 1차에 추가하지 않는다.
- 네이버 메일 한 계정을 연결한다. 기존 개인 도구에서 경험한 제공자로 먼저 검증하되 개인 키체인·회사별 예외·Notion 규칙을 서비스에 그대로 가져오지 않는다.
- 사용자는 본인 OpenAI API 키가 필요하다. 개발자가 아닌 사용자도 발급할 수 있게 설정 화면 안에 가입·결제·사용 한도·키 발급 단계와 OpenAI 화면 링크를 안내한다. ChatGPT 구독과 API 요금이 별개임을 알린다.
- 이력서 한 개를 텍스트 PDF 또는 MD로 등록한다. 새 문서 확인 성공 후 교체하며 실패하면 기존 문서를 유지한다. 스캔·암호화·손상 PDF는 지원 불가 사유와 MD/텍스트 PDF 재등록 경로를 제공한다.

### 1차에 제공하는 기능

1. 초대 계정 로그인·로그아웃과 사용자별 데이터 분리.
2. 네이버 연결 검사·연결 해제·재연결. 미연결 수동 이용 허용.
3. 이력서 업로드·추출 결과 확인·교체·삭제.
4. 직무·관련 경력·지역·고용형태·업무/도구/기술 설정. 희망 직무 복수 선택 가능.
4-1. 본인 OpenAI API 키 등록·확인·삭제와 모델 선택(모델별 판정 정확도 안내).
5. 세 출처의 공고 수집·추천·근거·마감·마지막 확인 및 확인 가능한 기업 유형·규모 표시.
6. 원문·지원 페이지를 기본 브라우저로 열기. 실제 제출은 사용자가 수행.
7. 지원 직접 등록·주요 상태 변경·검색·상태 필터·상세 근거.
8. 네이버 증분 조회·대상 연결·상태 반영·열람 표시.
9. 모호·연결 불명·최종 결과 충돌을 확인 목록에서 해결.
10. 앱 내 갱신 결과·최근 성공·실패·다시 시도 표시.
11. 서버에서 하루 한 번 예약 실행 및 명시적 수동 갱신. 자동 ON/OFF 제공.
12. 지원 건·문서·연결·계정 삭제 및 최소 이벤트·오류 기록.

1차도 저장·연동·수집이 실제로 작동해야 한다. 가상 데이터·정답을 입력한 예제·목업 화면은 개발 중 시험 자료이며 완료 근거가 아니다.

## 4. 1차 사용 흐름과 화면

가입 안내·초대 로그인 → 네이버 연결 또는 건너뛰기 → 이력서·필터 등록 → 추천 확인 → 외부 지원 → 접수 메일/사용자 확인 → 결과 갱신 → 확인 목록 처리.

- 최초 메일 조회는 최근 3개월 고정 기본값을 안내하고 동의받는다. 조회 기간 선택 UI·범위 확장은 2차로 이동한다.
- 메일 가져오기는 서버에서 진행하고 사용자는 이력서·필터를 설정한다. 준비된 지원 내역은 이력서 등록 전에도 확인 가능하다.
- 이력서·필터가 있어야 맞춤 추천한다. 메일 미연결이면 지원을 직접 등록·수정한다.
- 복잡한 온보딩 단계 엔진 대신 저장한 현재 설정을 다시 열어 이어서 입력할 수 있게 한다.

| 설정 | 네이버 연결·이력서·필터·자동 ON/OFF·삭제 |
| 갱신 결과 영역 | 처리중·성공·일부 실패·실패·최근 성공·재시도 |

같은 항목을 별도 페이지·모달·대시보드로 중복 구현하지 않는다. 검색·선택·기본 접근성·로딩·오류는 기본 사용성에 포함한다.

## 5. 1차부터 유지하는 추천·상태·정정 원칙

### 추천

- 사용자가 확인한 프로필·필터와 공고의 명시 정보로 후보를 분류하고 맞는 이유·불충족·미확인을 표시한다.
- 사용자가 정하는 선호(직무·근무 지역·원격 포함·고용 형태·요구 경력 상한)는 모두 사용자가 고르는 공고 필터다. 서비스가 이력서로 추정하거나 기본값을 넣지 않으며, 비어 있으면 제한하지 않는다. 필터는 공고 수집 요청과 추천 목록에 그대로 적용하고 화면에 현재 필터를 보여 준다(사용자 원칙 2026-11-08).
- 필수 조건이 명확히 불충족이면 기본 추천에서 제외한다. 최소 경력 부족은 도전 표시, 필수 정보 불명은 미확인 표시로 구분하고 목록 필터로 볼 수 있게 한다. 세 개의 독립 피드·세밀한 복구 UI는 만들지 않는다.
- 우대 일치는 순서에 반영하되 우대 부족만으로 제외하지 않는다. 점수·합격 확률·사용자 행동 기반 학습은 제공하지 않는다.
- 서류 미기재와 경험 부족, 총 경력과 직무 경력, 동의어와 유사 기술을 구분한다. 확인할 수 없으면 미확인으로 둔다.
- 직무·경력·필터의 단순한 구조화 사실과 근거 설명부터 구현한다. 1차에서 고도화된 개인화 학습을 완료 조건으로 삼지 않는다.
- 프론트엔드·앱 개발·디자인·기획 각각의 직무 분류·관련 경력·필수/우대 조건 사례로 추천을 검증한다. 개발 기술만으로 디자인·기획 적합성을 평가하지 않고 해당 직무의 업무·도구·경험을 근거로 사용한다.
- 관심 없음은 해당 공고 숨김과 해제를 제공한다. 회사 전체 차단·비슷한 공고 학습·조건별 피드백 분석은 2차다.

### 개인 상태와 공고 상태

| 개인 상태 | 의미 |
|---|---|
| 미지원 | 추천·저장 또는 사용자 미지원 확인 |
| 지원 완료 | 명확한 접수 메일 또는 사용자 확인 |
| 전형 진행중 | 서류 통과·과제·면접 안내 |
| 합격 | 명확한 최종 합격 또는 사용자 확인 |
| 불합격 | 명확한 서류·면접 불합격 또는 사용자 확인 |

- 열람은 별도 속성. 미열람과 열람 정보 없음을 구분한다.
- 공고는 모집중·마감·미확인으로 별도 관리한다. 공고 종료만으로 개인 상태를 불합격으로 바꾸지 않는다.
- 확인된 마감 정보로 모집 상태를 표시한다. 기한·종료 근거가 없으면 임의 종료하지 않고 최근 확인 시각을 보여준다.
- 지원하기 클릭만으로 지원 완료를 만들지 않는다. 같은 회사의 다른 직무·재지원 회차는 별도 지원이다.
- 메일만으로 모든 플랫폼 상태를 알 수 있다고 약속하지 않는다. 열람·결과가 메일에 없으면 직접 수정한다.

### 메일·확인·정정

- 공고/접수 식별자 → URL → 회사+직무+회차·시간 관계 순으로 연결한다. 회사명만 같거나 후보가 하나뿐이라는 이유로 확정하지 않는다.
- 접수 없이 결과만 있어도 회사·직무·결과가 명확하면 지원 건을 만들 수 있다. 실제 지원일은 미확인으로 남긴다. URL은 필수가 아니다.
- 회사 없는 메일·홍보는 상태 반영에서 제외한다. 결과가 외부 확인이거나 불명확하면 모호로 둔다.
- 기존 건이 없는 모호한 메일은 미확정 확인 요청으로 두며 지원 완료·합격 등으로 임의 집계하지 않는다.
- 메일 없는 수동 지원은 입력 상태를 유지한다. 단순 근거 대기는 확인 요청 수에 넣지 않는다.
- 확인 목록은 연결·결과 확정·무시만 제공한다. 미처리 항목은 남겨 두며 반복 모달로 재촉하지 않는다. 같은 근거는 재요청하지 않는다.
- 수동 지원 등록·진행 사실 확인은 영구 잠금이 아니다. 이후 명확한 새 전형은 반영한다.
- 잘못된 판정·연결을 정정하면 그 근거의 잘못된 재적용을 막는다. 새로운 독립 근거는 재평가한다.
- 오래된 접수·열람은 최신 결과를 되돌리지 않는다. 최종 결과 충돌·대상 또는 최신성 불명은 현재 값을 유지하고 확인받는다.
- 필드별 명시적 잠금·잠금 해제·보류 예약·복잡한 복구 UI는 2차로 미룬다. 최소 변경 이력과 같은 근거 재적용 방지는 1차에 남긴다.

## 6. 1차 자동 실행·권한·운영

- 서버에서 하루 한 번 메일 조회 → 공고 수집 → 추천 갱신을 실행한다. 정확한 시각은 배포 설정으로 정하며 매일 21시를 초기 후보로 둔다.
- 수동 메일 조회·공고 가져오기·추천 재계산은 작업 종류를 구분한다. 같은 종류의 중복 요청은 진행 작업에 합류시킨다.
- 공고는 사용자별 갱신으로 수집해 그 사용자 자료로만 저장하고 각자의 프로필과 본인 AI 키로 추천을 계산한다. 기본 브라우저·사용자 컴퓨터 화면을 자동 조작하지 않는다.
- 앱 완전 종료·컴퓨터 꺼짐 상태에서도 서버 작업이 실행되어야 한다. Electron 상주를 자동화의 조건으로 삼지 않는다.
- 1차 초대 계정에는 테스트 자동화 권한을 부여한다. 자동 ON/OFF는 실제로 동작해야 하며 결제 상태는 만들지 않는다. 예약 실행도 사용자 본인 키로만 AI를 호출한다.
- 자동 OFF·연결 해제·테스트 권한 회수 시 새 예약 작업은 실행하지 않는다. 이미 반영된 자료는 유지하고, 진행 중 자동 작업은 반영 직전 권한을 다시 확인한다. 수동 요청은 별도로 처리한다.
- 앱에는 갱신 결과·최근 성공·적용·확인 요청·실패 건수를 표시한다. 1차는 트레이·OS 알림·실시간 진행 푸시 없이 실행·재실행 시 서버 상태를 읽는다.
- 창 닫기·종료는 서버 자동화 중단과 다르다. OS 기본 종료 동작을 따르고 명확한 완전 종료를 제공한다.
- 개발 단계에서는 가격·운영비 계산·매출 목표를 작업에 넣지 않는다. 실패·처리 시간·사용자 정정은 기록해 품질을 판단한다.

### 배포·사업화 아이디어 (보류)

- 랜딩 페이지를 통한 공개 배포는 하지 않는다(사용자 결정 2026-11-10). 수집한 공고를 불특정 다수에게 제공하면 원티드·자소설닷컴 약관과 채용공고 크롤링 판례에 정면으로 걸리고, 오픈소스 자기 실행은 개발자만 쓸 수 있다.
- 사업화를 다시 검토한다면 공고 수집이 아니라 데이터를 모으지 않는 가치로 옮긴다: 사용자 본인 메일 기반 지원 관리·자동 반영, 사용자가 보고 있는 공고를 이력서와 대조하는 브라우저 확장 판정. 이 경우 AI 비용·요금 구조를 새로 정한다.

### 필요성을 다시 검증할 기능

본인 GPT·Claude 계정 로그인 연결·OpenAI 외 제공자, Linux, HWP/HWPX, 자기소개서 별도 종류, 문서 버전 복구·실제 제출본 보관, Excel·Notion 연동, 상세 일정 캘린더·예약 알림은 필요성을 다시 검증한다. 자동 지원·메일 발송은 현재 서비스 범위에서 제외한다.

## 8. 1차에 미룰 수 없는 보호와 검증

- 사용자 인증·데이터 격리·비공개 파일 접근·비밀정보 보호·연결 해제·데이터 삭제를 제공한다. 비공개 테스트라는 이유로 생략하지 않는다.
- 메일 읽음·삭제·이동·회신을 하지 않는다. 일반 메일 원문·연락처·인증정보를 로그·분석·프로젝트 파일에 저장하지 않는다.
- 외부 AI 처리 시 제공자·전달 범위·목적을 안내하고 필요한 정보만 사용한다. 불명확한 결과를 자동 확정하지 않는다.
- Electron 웹 화면에 Node·파일시스템 전체 권한을 주지 않는다. 외부 링크·인증 복귀·세션을 검증한다.
- 원장·지원 ID·출처·메시지 ID·정정 근거는 처음부터 저장해 2차 추가 시 기존 사용 기록을 버리지 않는다.

### 1차 완료 조건

1. 웹 브라우저로 서버에 접속해 로그인하고 이력서·필터·지원 건을 저장한 뒤 다시 접속해 확인한다.
2. 원티드·잡코리아·자소설닷컴 세 출처의 실제 공고를 자동 수집해 추천 이유·마감·지원 링크를 제공한다. 공고는 갱신한 사용자 자료로만 저장되고 AI 처리는 그 사용자의 키와 선택 모델로 한다. 키 없음·잘못된 키·잔액 부족은 원인별로 표시된다. 프론트엔드·앱 개발·디자인·기획 각각을 검증하며 수집 실패는 드러나야 한다. 기업 유형·규모 미확인은 사실처럼 채우지 않는다.
3. 네이버 연결과 초기 조회·증분 조회·재연결이 실제로 작동하고 같은 메일을 반복 처리해도 중복되지 않는다.
4. 접수 → 전형 진행중 → 최종 결과와 열람이 정책대로 반영되고 모호한 결과는 확인 목록에서 해결된다.
5. 같은 회사 다른 직무·결과만 있는 메일·URL 없는 메일·회사 없는 메일·오래된 메일·정정 재처리를 검증한다.
6. 앱을 완전히 종료한 동안 예약된 서버 작업이 처리되고 다음 실행에서 결과가 보인다. 자동 OFF·연결 해제는 후속 예약 처리를 막는다.
7. 공고 마감은 개인 불합격으로 바뀌지 않으며 회사·직무 오연결·근거 없는 최종 결과·데이터 혼합이 필수 사례에서 발생하지 않는다.
8. 파일 실패 시 기존 이력서 유지, 사용자별 접근 차단, 연결·서류·지원·계정 삭제, 오류 재시도가 동작한다.
9. 운영자가 2주 동안 매일 사용한 기록(갱신 횟수, 기본·도전 건수, 실제 지원 건수, 정정·확인 처리 건수)과 초대 지인 1~2명의 의견으로 추천 유용성·정정 부담을 판단하고, 발견한 오류의 재현·수정 여부를 정리한다.

정답 표본의 연결 정확도·상태 판정·누락을 분리 측정한다. 특정 사례 통과를 전체 무오류 보장으로 표현하지 않는다. 표본만으로 주장할 수 없는 정확도 목표를 임의로 약속하지 않는다.

## 9. 문서의 우선순위와 남은 결정

이 문서의 단계별 범위가 과거 대화와 이전 화면 구상의 ‘첫 출시’ 표기보다 우선한다. 화면의 현재 사실은 구현(`apps/web`)이 가진다.

세 출처와 1차 직무 범위는 확정했다. 남은 착수 결정과 그것이 막는 단계는 [백로그의 미결 결정](gap-analysis.md#미결-결정)이 소유한다. Windows 세부 배포·Gmail 연결 준비는 해당 2차 작업의 선행 조건으로 둔다. 가격·구독은 두지 않는다(2026-11-10).

최소 데이터 구조·2차 확장 시 마이그레이션·기술 검증은 [기술 설계 부록](기술설계_부록.md), 1차 구현 순서와 현재 상태는 [백로그](gap-analysis.md)를 따른다. 이번 개정은 계획 문서만 변경했다.
