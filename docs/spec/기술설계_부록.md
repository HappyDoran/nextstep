# 기술 설계 부록 — 1·2차 구현 계획

개정일: 2026-11-04
기준: [서비스 기획서 v0.2](서비스기획서_v0.2.md). 실제 코드·인프라 구현은 수행하지 않음. ‘1차’는 비공개 MVP, ‘2차’는 공개 베타 확장이다. 이전의 전체 공개 서비스 구성을 모두 1차 요구로 해석하지 않는다.

## A. 1차 구조와 생략할 구성

`Electron(macOS, HTTPS 웹 UI) → 단일 서비스 API → 관계형 DB·비공개 파일 저장소`

같은 서버 환경에 작업자 한 개와 서버 예약 실행을 둔다. 메일·공고·서류 추출은 화면 요청과 분리해 작업 기록을 남기고 처리한다. Redis·전용 메시지 브로커·여러 마이크로서비스·실시간 WebSocket은 1차 필수로 도입하지 않는다.

- 클라이언트는 작업 ID로 상태를 확인한다. 처리중일 때만 제한적으로 조회하고 완료 후 멈춘다. 앱 재실행 시 최근 작업 결과를 읽는다.
- DB에 대기·실행중·성공·일부 실패·실패를 기록한다. 사용자/연결/작업 종류별 중복을 합치고 작업 중 서버가 중단되면 재시도할 수 있어야 한다.
- 작업은 원자적으로 선점하고 실행 만료 시각을 둔다. 재시작 후 남은 실행중 작업을 복구하되 같은 이벤트를 두 번 반영하지 않는다. 작업자 한 개여도 내구성·중복 방지를 생략하지 않는다.
- 서버 예약은 하루 한 번을 초기값으로 한다. 정확한 시각은 배포 설정, 21시는 후보. 수동 요청과 같은 처리 경로를 사용한다.
- 구현(P1-06): 서버 프로세스의 예약 검사기가 1분마다 한국 시간 기준 `NEXTSTEP_SCHEDULE_HOUR`(기본 21시) 이후 `초대 테스트 권한 AND 자동 ON` 사용자에게 이력서·프로필이 있으면 갱신, 메일 연결이 정상이면 메일 작업을 만든다. 사용자·날짜·종류별 한 번만 만들고(재시작해도 중복 없음) 같은 종류 대기 작업이 있으면 재사용한다. 자동 OFF·연결 해제 시 대기 작업을 지우고 실행 중 작업은 마친다. 설정 화면은 최근 예약 실행 결과를 보여 준다.
- 자동화 조건은 `자동화 권한 유효 AND 자동 ON AND 필요한 연결 정상`이다. 1차 권한 공급원은 초대 테스트 권한, 2차는 구독 상태로 확장한다.
- 자동 작업 등록·실행·반영에서 권한을 확인한다. OFF·연결 해제 시 새 예약은 중단하고 진행 작업은 안전하게 중단·대기로 정리한다. 사용자의 명시적 수동 요청과 구분한다.
- 앱 종료·컴퓨터 꺼짐은 서버 중단 조건이 아니다. 모든 처리 작업을 Electron 로컬 타이머로 구현하는 방식을 사용하지 않는다.

관계형 DB를 사용하되 업체·엔진 세부 선택은 착수 설정으로 남긴다. 원본 파일은 비공개 저장소, 연결 비밀정보는 별도 암호화·접근 통제 경로로 관리한다. 1차에서 공개 사용자에게 사용할 배포를 실행한다는 뜻은 아니다.

## B. 최소 데이터 모델과 지금 필요한 확장 지점

아래는 개념 객체이며 객체 하나마다 서비스·별도 화면·복잡한 테이블 체계를 만들라는 요구가 아니다. 조회·정합성에 따라 관련 필드를 묶되 사용자 경계와 근거는 유지한다.

| 객체 | 1차에 저장할 내용 | 2차 연결점 |
|---|---|---|
| 사용자·권한 | 사용자 ID·인증 주체·초대 자동화 권한·자동 ON/OFF | 공개 가입·구독이 같은 권한을 공급 |
| 메일 연결·위치 | 사용자·provider·제공자 계정 ID·비밀정보 참조·연결 상태·편지함별 확보 위치 | Gmail historyId·새 계정 추가. 네이버 위치를 재사용하지 않음 |
| 활성 문서 | 사용자·kind·원본 키·추출 본문·확인 사실·교체 시각 | portfolio/career 및 추출 방식 추가. 이력서 덮어쓰기 금지 |
| 프로필·필터 | 확인된 직무·경력·지역·고용형태·기술·갱신 식별 | 새 직군·조건을 추가. 원본 사실과 추정 구분 |
| 공고·출처 | 내부 공고 ID·출처 ID·출처별 공고 ID/URL·본문의 구조화 사실·마감·확인 시각·확인 가능한 기업 유형/규모와 근거 | 새 수집기를 같은 구조로 정규화. 회사명만으로 통합 금지 |
| 추천·숨김 | 사용자·공고·기준 프로필/문서 식별·근거·후보 분류·숨김 | 선호·상세 피드백 추가. 과거 추천을 새 기준으로 위장하지 않음 |
| 지원 | 내부 ID·사용자·회사·직무·회차·선택 공고 참조·개인 상태·열람·수동 관리 | URL은 기본키가 아님. 새 출처·조회와 무관하게 유지 |
| 메시지·이벤트·정정 | provider/계정/메시지 ID·최소 근거·발생/수신 시각·대상·결과·정정 이력·재적용 억제 | 제공자 간 중복은 보조 식별로 대조. 원본 ID는 보존 |
| 확인 요청 | 연결 불명·모호·최종 결과 충돌·근거·선택 대상·처리/무시 | 보류·잠금·고급 비교 UI 추가. 기존 처리 결과 보존 |
| 작업·결과·최소 이벤트 | 작업 ID·소유자·종류·멱등 키·상태·시도·최근 성공·오류 코드·건수 | 별도 큐·운영 분석 도입 시 작업 ID·결과 계약 유지 |

provider·문서 kind·출처 ID를 문자열/명시 코드로 다루고 두 번째 연결 시 기존 ID 의미가 바뀌지 않게 한다. 아직 없는 기능을 위해 범용 플러그인 프레임워크·전 직군 대형 분류 체계·결제 테이블을 미리 구현하지 않는다.

## C. 1차 네이버 조회·판정·정정

### 연결과 증분 처리

- 네이버 한 계정, IMAP 설정·앱 비밀번호·TLS·읽기 전용 조회. 기존 개인 키체인을 신규 사용자 인증 저장소로 사용하지 않는다.
- 최초 최근 3개월 조회는 기간 안내·동의 후 실행한다. 여러 기간 선택·과거 범위 확장 UI는 2차다.
- 구현(P1-05 기반): 연결 정보는 사용자당 하나이며 비밀번호는 DB와 다른 키로 암호화한다. 작업자는 편지함별 UIDVALIDITY·마지막 UID 이후만 조회하고(실행당 편지함별 300건, 남으면 다음 실행), 메일 처리를 저장한 뒤 위치를 전진시킨다. 메시지 키(Message-ID, 없으면 편지함·UIDVALIDITY·UID)로 중복을 막는다. 저장 근거는 수신 시각·제목 앞 80자·짧은 발췌·공고 키다. 공고 키로 지원 건이 하나만 맞으면 순서(미지원<지원 완료<전형 진행중<최종 결과)를 거스르지 않을 때만 반영하고, 최종 결과 충돌·모호는 확인 요청을 만든다. 공고 키가 수집 공고와 맞으면 지원 건을 만들고 지원일은 만들지 않는다. 식별하지 못한 메일은 `unlinked`로 보관하고 편지함·UIDVALIDITY·UID만 남긴다. AI가 설정되면 같은 작업에서 본문(이번 실행분은 메모리, 이전 보관분은 읽기 전용 재조회)을 OpenAI로 해석해 채용 무관이면 제외, 회사·직무·결과가 명확(high)하고 같은 회사·직무 지원 건이 하나면 반영, 없으면 지원 건 생성(지원일 미생성), 같은 회사 다른 직무·확신 낮음·모호면 확인 요청으로 넘긴다. 실행당 60건, 메일당 3회까지 시도한다. 무시·연결 해제 시 삭제한 근거는 억제 목록에 남긴다.
- 실제 계정 검증(2026-11-07): 3회 증분 실행에서 채용 메일 542건 저장, 중복 0건, 확보 위치 전진, 합격 판정은 안내 문구 오판을 막은 뒤 6건.
- 네이버 IMAP 노출 상한은 계정 설정 "IMAP 동기화 메일 제한"(환경설정 > POP3/IMAP 설정 > IMAP/SMTP 설정, 기본 1,000통, 선택 1,000~5,000통, 무제한 없음)이다(2026-11-07 확인). 계정당 최대 5,000통을 전제로 하고, 범위 미달이면 설정 위치를 안내한다.
- 네이버 받은편지함은 P1-01에서 정확히 1000건만 노출됐다. 최초 조회는 편지함에 노출된 가장 오래된 메일이 조회 시작일보다 늦으면 범위 미달을 사용자에게 표시하고 완료로 보고하지 않는다.
- 수신·분류 폴더를 포함하고 프로모션 등에 있는 결과 메일 누락을 점검한다. 보낸·임시·휴지통·스팸은 1차 기본 조회에서 제외한다. 스팸 포함 선택은 2차로 두고 1차 조회 범위를 명시한다.
- 편지함별 UIDVALIDITY·확보 UID를 기록한다. P1-01에서 네이버 받은편지함이 RFC와 달리 UIDVALIDITY 0을 반환했으므로 UIDVALIDITY만으로 초기화를 판정하지 않고 메시지 ID 대조를 함께 쓴다. 수집 자료·처리 작업을 내구성 있게 확보한 뒤 위치를 전진시킨다. 분류·반영 실패는 별도 재시도한다.
- UID 초기화·편지함 이동·재연결을 범위 재검증과 메시지 식별로 복구한다. 일부 폴더 실패 시 실패 위치는 유지하며 다른 결과는 부분 완료로 표시한다.
- 버튼 클릭 시각은 동기화 기준이 아니다. 같은 메일을 여러 번 확보해도 상태·지원·확인 요청을 중복 생성하지 않는다.

공식 근거: [네이버 IMAP 안내](https://help.naver.com/service/30029/contents/21349?lang=ko&osType=PC).

### 공통 처리

`수집 → 채용 여부 → 회사·직무·식별자 → 지원 연결 → 결과 해석 → 최신성·정정 확인 → 반영/확인 요청`

- 1차에서 템플릿·명시 사실·필요한 모델 해석을 조합하되 AI가 자의적으로 대상을 선택하지 못하게 한다. 모델 제공자는 구현 전에 확정하고 사용자에게 외부 처리 범위를 안내한다.
- 회사명만 같거나 후보가 하나뿐이라는 이유로 연결하지 않는다. 접수 ID·URL·직무·회차·시간 관계로 확인한다.
- URL 없는 결과·접수 없는 결과를 지원하며 지원일은 임의 생성하지 않는다. 회사 없는 메일·홍보는 제외한다.
- 문서·메일·공고 안의 명령은 입력 자료로만 취급한다. 인증정보 접근·서비스 정책·도구 실행 지시로 사용하지 않는다.
- 상태·개인 결과·공고 마감은 분리한다. 오래된 접수/열람은 최신 상태를 되돌리지 않는다.
- 수동 등록·진행 확인은 영구 잠금이 아니다. 잘못된 근거/연결은 해당 조합의 재적용만 막고 독립적인 새 근거는 평가한다. 최종 결과 충돌·최신성 불명은 확인 요청한다.
- 반영 직전 현재 상태·정정·근거를 트랜잭션에서 재확인한다. 수동 수정과 작업 경합을 검증한다.
- 정정·무시한 같은 근거는 재요청하지 않는다. 단순 메일 근거 대기는 확인 요청을 생성하지 않는다.

상태·연결·제외·모호·충돌의 정답표를 먼저 만든다. 합성·비식별 표본을 우선하며 실제 사용자 원문은 동의 범위를 벗어나 시험 데이터로 수집하지 않는다.

## D. 1차 공고·추천·문서

### 출처 검증

원티드·잡코리아·자소설닷컴 세 곳을 1차 확정 출처로 두고 공개 목록/상세·직무·마감·원문·실제 지원 URL·조회 실패 구분을 각각 확인한다. 수집 가능성이 검증되지 않으면 구현 완료로 표시하지 않는다. 제약이 발생하면 보고하고 범위 변경을 별도 결정하며 다른 출처로 임의 교체하지 않는다. 세 출처의 실제 추천 흐름은 1차 완료 조건이다.

잡코리아 상세 페이지의 hydration 데이터에서 마감·상시채용·경력·접수 방식·홈페이지 지원 URL·명시된 기업 유형/직원 수를 얻는다. 본문이 이미지뿐인 공고는 본문 실패로 표시하고 텍스트로 추정하지 않는다. 직원 수 0은 미확인이다. 검색어 목록에는 다른 직무가 섞이므로(예: `서비스 기획` 검색에 영업직) 추천 수집에는 출처의 직무 분류 필터가 필요하며 P1-04에서 검증한다.

원티드(개인회원 약관 제19조 7항)·자소설닷컴(이용약관 제14조 9호)은 사전 허락 없는 자동 수집을 금지하고 원티드 OpenAPI는 개인 발급이 불가하다. 세 출처 모두 얻은 정보의 사전 동의 없는 제3자 제공을 금지한다. 채용공고 크롤링을 데이터베이스제작자 권리 침해로 본 판례(서울고법 2016나2019365)가 있다. 그래서 수집 모드를 서버 설정으로 두고 출처별 접근을 공통 계약 `SOURCE_POLICY`로 정한다.

| 출처 | 서비스 모드 | 개인 모드 |
|---|---|---|
| 잡코리아 | 자동 수집. 원문은 판정에만 쓰고 링크·제목·회사·마감·판정 근거만 저장 | 자동 수집 |
| 원티드·자소설닷컴 | 사용자가 넣은 공고 링크 한 건만 조회·판정 | 공개 페이지 자동 수집 |

- 모든 모드에서 로그인하지 않고, 403·429를 받으면 그 호스트 요청을 멈추며 IP 변경·캡차 우회를 하지 않는다. 수집기는 실행 전에 현재 모드의 출처 접근을 확인하고 자동 수집이 아니면 요청하지 않는다.
- 개인 모드 목록 확보: 원티드는 목록 HTML에 공고 링크가 없어 웹 화면이 쓰는 공개 목록 JSON을 직무 태그로 조회하고, 자소설닷컴은 웹 화면이 쓰는 공개 직무별 목록(직무 분류 ID: 프론트엔드 175·웹 162, 앱 161·172·173, UI·UX 241, 서비스기획·PM 171)을 쓴다. sitemap은 직무 정보가 없어 대상 공고를 찾지 못했다. 상세는 두 출처 모두 공개 페이지의 `__NEXT_DATA__`를 읽는다.
- 원티드 상세에는 기업 유형·규모가 없어 미확인이다. 자소설닷컴 본문은 대부분 이미지라 1차에서는 모집 분야 문구로만 판정하고 본문은 미확인으로 둔다(OCR은 2차).
- 개인 모드 수집 결과는 운영자 한 명의 자료이며 다른 사용자 추천에 섞지 않는다. 모드를 서비스로 바꾸면 개인 모드로 수집한 원티드·자소설닷컴 자료를 다른 사용자에게 노출하지 않는다.
- 메일 알림에서 공고를 얻는 방식은 후보를 플랫폼이 정하고 본문이 없어 이력서 대조가 불가능해 채택하지 않았다.

선정 이유는 사용자 요구에 따른 공고 탐색 범위 확보 및 스타트업·기업 규모 비교다. 기업 유형/규모는 해당 공고·기업 소개의 명시 사실과 근거가 있을 때만 저장·표시한다. 정보 없음은 미확인으로 두고 플랫폼 이름만으로 스타트업·대기업을 추정하지 않는다. 별도 기업정보 크롤러·추정 모델은 1차에 추가하지 않는다.

공통 저장소에 출처별 공고를 저장하고 사용자 필터로 추천한다. 목록 수집·추천 재계산·모집 상태 확인을 구분한다. 필터 변경은 기존 데이터로 먼저 계산하고 재수집 여부·확인 시각을 표시한다. 공고 마감 재확인은 정기 수집과 명시적 새로 가져오기에 포함한다. 지원 직전 강제 재조회·다섯 출처 요일별 최적화는 2차로 이동한다.

### 추천과 추출

- 구현(P1-04): 갱신은 사용자별 작업(대기·실행중·성공·일부 실패·실패)으로 처리한다. 작업자는 수집 모드에 따라 직무별 소량(출처별 직무당 5건)을 모으고, 공고 원문은 OpenAI 조건 추출(직무군·필수·우대·원격·포트폴리오 필수)에만 쓰고 추출 결과만 저장한다. 판정은 저장한 프로필·이력서 일부·공고 사실로 하며 프로필 저장 시각·이력서 ID·프롬프트 버전이 같으면 다시 판정하지 않는다. 실행당 판정 상한은 40건이다. 사용자가 넣은 링크로 가져온 공고는 그 사용자 전용이다.

- 프론트엔드·앱 개발·디자인·기획의 확인된 조건·경력·업무·도구·경험을 기준으로 기본/도전/미확인 분류와 근거를 제공한다. 앱 개발에는 iOS·Android·크로스플랫폼을 포함한다. 필수·우대·미기재를 구분한다.
- 복수 직무는 OR, 다른 필수 조건 그룹은 AND. 동의어와 유사 경험으로 명시적 필수 경력을 위조하지 않는다.
- 정답 사례(`apps/server/tests/prompts/recommendation-cases.json`)가 정한 초기 판정 규칙: 제외 > 도전 > 미확인 > 기본 순으로 우선한다. 같은 직무 연차 부족은 폭과 무관하게 도전, 다른 성격의 필수 경력(예: UX 리서치·PO 직책·특정 기술 실무)은 유사 경험으로 대체하지 않고 제외한다. 이력서에 없는 단순 필수 기술·포트폴리오 필수·역할 수준(리딩)은 미확인이다. 서울 밖 사무실은 전면 원격일 때만 기본, 근무지 미기재는 미확인, 마감은 기준 시각으로 비교해 지나면 제외한다. 디자인은 UI/UX·프로덕트 디자인, 기획은 서비스 기획·PM/PO만 대상이며 공간·패션 디자인, 사업·상품·영업기획은 제외한다. 사용자가 확정했다(2026-11-07).
- 초기 추천 규칙과 정답 사례를 프론트엔드·앱 개발·디자인·기획 각각에서 확인한다. 디자인·기획은 개발 기술 중심 규칙을 그대로 적용하지 않고 해당 업무·도구·경험을 평가한다. 백엔드·마케팅 등 추가 직무, 전 직군 분류·피드백 학습·개인화 점수 최적화는 2차 범위다.
- 텍스트 PDF·MD 이력서 한 개. 추출 본문·경력·기술은 사용자가 확인한다. PDF/MD 파일당 20MB를 초기값으로 사용한다.
- 업로드는 서버 크기·유형·처리 시간 제한을 적용한다. 암호화·손상·스캔 PDF 미지원은 실패로 표시하고 텍스트 PDF/MD 등록을 안내한다. 실행 파일·임의 경로 접근을 허용하지 않는다.
- 새 문서 확인 성공 후 대표를 교체하고 기존 원본·본문을 삭제한다. 실패·취소 시 기존 대표를 유지한다. 삭제된 구 문서 ID는 추천 기준 식별용 최소 메타데이터만 남긴다.

## E. 1차 Electron·보호·배포

- macOS 개발 환경에서 Electron은 서비스 소유 HTTPS 웹 UI를 표시한다. 로컬 개발 주소는 개발 모드에서만 별도 허용하며 임의 외부 화면으로 이동시키지 않는다.
- nodeIntegration 비활성화, contextIsolation·sandbox 적용, 최소 preload/IPC만 제공한다. 네이티브 기능·파일 경로·전체 IPC 접근을 renderer에 노출하지 않는다.
- 지원·원문·외부 결과는 기본 브라우저로 열고 URL·스킴을 검사한다. 서비스 로그인·인증 방식에 맞는 검증된 세션과 복귀 처리를 구현한다.
- 트레이·자동 실행·데스크톱 알림·자동 업데이트는 1차에서 제외한다. 기본 OS 창 종료와 완전 종료를 제공한다. 서버 자동 OFF는 별도 설정이다.
- 서버 작업은 별도 환경에서 실행되어야 하며 사용자의 앱·노트북을 켜 두어야만 작동하는 상태는 완료가 아니다.
- 앱 재실행·세션 만료·절전 복귀·네트워크 복구 시 현재 서버 결과를 조회한다. 오프라인 편집은 제공하지 않고 연결 안내·재시도를 제공한다.
- 1차 비공개 설치는 수동 교체·재설치 안내로 운영한다. 업데이트 주체·버전은 관리하고 취약한 앱을 방치하지 않는다. 두 OS 서명·배포 자동화·호환성 안내는 2차 공개 제공 전에 완료한다.

[Electron 보안](https://www.electronjs.org/docs/latest/tutorial/security), [트레이](https://www.electronjs.org/docs/latest/tutorial/tray), [업데이트](https://www.electronjs.org/docs/latest/tutorial/updates).

### 보호·삭제는 1차 필수

- 개인 데이터는 모두 사용자 소유·접근 범위를 강제하고 비공개 파일 URL·다운로드 권한을 검사한다. 다른 사용자 ID를 보내도 접근할 수 없어야 한다.
- 원본·추출문·메일과 인증정보는 DB/파일/비밀정보 저장 경계를 나눈다. renderer 저장소·로그·프로젝트 파일에 평문 자격정보나 메일 원문을 남기지 않는다.
- 연결 해제는 조회 중단·비밀정보 삭제, 기존 지원은 유지/삭제 선택. 지원 삭제 시 같은 과거 근거로 재생성되지 않도록 최소 억제 식별을 둔다. 계정 삭제 시 사용자 근거·파일·억제 식별까지 삭제한다.
- 작업 취소·삭제와 실행이 겹쳐도 삭제한 개인 정보·지원이 작업 종료로 되살아나지 않아야 한다.

| 자료 | 채택한 개발 초기값 |
|---|---|
| 일반 메일 원문 | 장기 저장하지 않음. 분류에 필요한 범위만 일시 처리 |
| 처리용 임시 본문 | 성공 후 즉시 삭제. 실패 시 최대 24시간 후 삭제·필요 시 제공자 재조회 |
| 채용 근거 | 메시지 식별·시각·최소 제목·짧은 비식별 근거·구조화 사실. 지원 존속 동안 유지 |
| 활성 서류 | 최신 한 개 유지, 교체·삭제 후 온라인 사본 24시간 내 제거 목표 |
| 오류·작업 로그 | 본문·인증정보 없이 30일 |
| 계정 삭제 | 작업·접근 즉시 차단, 온라인 자료 24시간 내 제거 목표 |
| 백업 | 최대 30일 만료 기본안. 복원 시 삭제 요청 재적용 |

구현(P1-07): 예약 검사기가 1분마다 30일 지난 끝난 작업·처리한 확인 요청·미사용 만료 초대와 만료 세션을 지운다. 채용 근거의 최소 키는 같은 메일 재처리 방지를 위해 계정 삭제 전까지 남긴다. 실제 삭제·백업 환경을 확인한 뒤 사용자 안내에 확정한다. 외부 AI의 보관까지 즉시 삭제된다고 약속하지 않는다. 기능이 비공개여도 필요한 외부 처리 설명·동의·접근 통제를 생략하지 않는다.

## F. 1차 구현 순서와 완료 증거

1차 구현 순서(P1-01~07)·선행 의존성·완료 증거와 현재 상태는 [요구사항 대비 현재 상태와 백로그](gap-analysis.md)가 소유한다.

### 관측과 통과 기준

1차는 작업 성공·실패·소요 시간·자동 적용·정정·확인 요청 생성/해결을 서버에 최소 기록한다. 운영자는 DB/서버 오류를 확인하고 복구할 수 있어야 한다. 원문·인증정보는 기록하지 않는다. GA4·Discord·분석 대시보드는 2차다.

회사·직무 연결 정확도·상태 판정·누락을 따로 평가한다. 오연결·근거 없는 최종 확정·마감에 의한 불합격·사용자 데이터 혼합은 필수 사례에서 발생하지 않아야 한다. 정량 공개 출시 목표는 실측 후 2차 공개 베타 전에 확정한다.

## G. 2차 연결 순서와 재작업 방지

### 2-A. 입력 범위 확대

- Gmail은 네이버 구현을 복제하지 않고 별도 제공자 수집기·인증·위치로 추가한다. 초기에는 수동 조회부터 증분·재연결·정답 연결을 검증한 뒤 자동 트리거를 붙인다.
- 사람인·점핏 두 출처는 출처별 추출·마감·지원 URL 검증 뒤 공통 공고로 변환한다. 점핏은 개발 직무에 적용하며 출처 간 통합은 확인 가능한 동일 공고에만 적용한다.
- 백엔드·마케팅 등 추가 직무는 필터 선택지만 늘리지 않고 직군별 경력·조건·추천 정답 사례를 추가한다. 프론트엔드·앱 개발·디자인·기획은 1차 범위이며 이미 검증한 결과로 새 직무 품질을 보장하지 않는다.

### 2-B. 문서·추천 확장

- 문서 kind·추출 방식 추가로 포트폴리오·경력기술서·ZIP·OCR을 연결한다. 기존 이력서·추천 이력을 덮어쓰지 않는다. 추가 서류는 미등록이 기본값이다.
- ZIP은 50MB·해제 후 200MB/500파일 초기값과 경로 이탈·압축 폭탄·실행 파일 차단을 실제 지원 전에 구현한다. 미지원 기간에는 ZIP 업로드 자체를 허용하지 않는다.
- 고급 필터·선호·피드백은 기존 공고 사실·필수 조건을 보존한 채 추천 계산을 확장한다. 사용자 피드백을 곧바로 회사·직무 전체 차단으로 해석하지 않는다.
- 과거 범위 확장은 별도 작업으로 수행하며 현재 커서를 초기화하지 않는다. 저장된 메시지 ID·정정 억제로 중복·과거 판정 재적용을 막는다.

### 2-C. 자동화·운영 고도화

- 15분 네이버 조회는 검증 초기값이며 Gmail은 Pub/Sub 변경 알림·구독 갱신·이력 만료 복구·정기 누락 확인을 추가한다. provider·계정·편지함별 위치를 분리한다.
- 처리량·복구 요구가 확인될 때 전용 큐·별도 작업자로 옮긴다. 작업 종류·멱등 키·기존 ID·권한 검사를 유지하며 1차와 2차 작업자가 같은 작업을 중복 선점하지 않게 전환한다.
- 명시적 잠금은 별도 설정으로 추가한다. 기존 수동 확인·정정을 전부 잠금으로 마이그레이션하지 않는다. 보류·같은 근거 무시·새 근거 재평가를 구분한다.
- GA4는 행동 분석, Discord는 개인정보 없는 집계·장애 경보로 추가한다. 기존 최소 이벤트를 필요한 형태로 전송하고 알림 실패가 상태 반영을 실패시키지 않게 한다. 상세 분석 이벤트 90일은 초기 보관안이다.

### 2-D. 클라이언트·공개 제공

- Windows·macOS 최소 버전·아키텍처·서명·패키징·설치·업데이트·인증 복귀·파일·트레이·알림을 OS별 검증한다.
- 트레이·데스크톱 알림은 서버 결과함의 새 표시 경로다. 앱 완전 종료 중 처리는 서버가 계속하고 즉시 데스크톱 알림을 보장하지 않는다. 시작 시 자동 실행은 기본 OFF.
- 자동 업데이트는 사용자가 재시작 시점을 선택하며 업로드·수정 중 강제 재시작하지 않는다. 원격 웹 UI와 Electron 브리지/API 호환성 범위를 검증한다.
- 결제는 기존 자동화 권한의 공급원으로 연결한다. 구독 만료가 기존 지원·메일 기록을 삭제하지 않으며 수동 조회는 유지한다. 중복 결제 이벤트·갱신·만료·자동 OFF·도중 해지를 검증한다. 가격·환불·약관은 배포 준비 단계에서 결정한다.

### 마이그레이션 원칙

2차 필드는 추가·기본값 방식으로 도입하고 원장·사용자·지원·메시지·이벤트 ID를 유지한다. 제공자/문서/출처가 늘어도 과거 자료를 재생성하거나 사용자의 정정을 제거하지 않는다. 호환되지 않는 변경은 데이터 이행·기존 클라이언트 대응·실패 복구를 먼저 확인한다. 아직 없는 전체 2차 스키마를 1차에 선구현하지 않는다.
