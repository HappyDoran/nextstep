# 맞춤 채용공고 추천·지원 관리 서비스 기획서

개정일: 2026-11-18 (아이콘 메뉴·갱신 결과 하단 상태바, 상세 모달, 단축키 없음). 
버전: 0.2.7. 모든 버전(현재 포함)은 [기획서 버전 기록](history/README.md)에 보관한다. 이 파일을 고치면 버전을 올리고 같은 내용을 history에 새 번호로 남긴다(구조 검사가 확인).
상태: 통합 범위 구현 중. 구현 현황은 [README](../../README.md#현재-구현-범위)와 [백로그](백로그.md)가 가진다.
적용 범위: 운영자와 초대 사용자만 쓰는 비공개·무료 서비스. 기존 개인 작업 공간의 Notion·메일·자동화 규칙 및 로컬 현황 생성물과 별개.

## 1. 서비스 방향과 범위 정의

이력서·선택 서류·희망 조건으로 여러 플랫폼의 공고를 추천하고, 사용자가 외부에서 지원한 후 메일과 수동 입력으로 진행 상황을 관리한다. 대상은 취업·이직 준비자다.

- **단계 통합(사용자 결정 2026-11-14).** 기존 1차(비공개 검증 MVP)와 2차(출처 추가)·7절 아이디어 중 아래 범위를 하나의 범위로 합쳐 홈서버 구축 단계에서 전체를 구현한다. 이유: 공개 배포를 하지 않고 실제로 쓰는 사람만 비공개로 쓰므로 단계별 공개 검증이 필요 없고, OpenAI 비용 부담을 없애려고 최종적으로 홈서버 로컬 LLM으로 옮긴다. 목표는 단계와 상관없이 범위 전체를 먼저 동작하는 수준으로 구현하는 것이다(사용자 결정 2026-11-14).
- **AI 전환 순서(사용자 결정 2026-11-14).** 구현 기간에는 OpenAI를 공고 추출 위주로 최소한만 써서 비용을 아끼고, 기능을 갖춘 뒤 마지막에 로컬 LLM으로 바꾸며 모델 측정·세부 조정을 한다.
- **개발·배포.** 개발은 운영자 Mac에서 하고, 웹(프론트엔드)과 API(백엔드)의 빌드·실행은 홈서버에서 한다.
- **운영 형태.** 운영자가 운영하는 홈서버 한 대(웹·백엔드·DB·작업자·로컬 LLM)를 운영자와 초대 링크로 가입한 사람만 Tailscale 사설망의 웹 브라우저 또는 데스크톱 상주 앱(Electron)으로 쓴다. 우선은 운영자 혼자 쓰고 초대 사용자는 그 뒤에 들인다(사용자 결정 2026-11-18). 초대 사용자는 Tailscale 계정을 만들고 운영자가 홈서버 기기를 공유해 접속한다. 접속은 HTTPS(Tailscale 인증서)로 한다(사용자 결정 2026-11-14). 공개 가입·결제·구독·스토어 출시·공개 배포는 하지 않는다.
- **완료 판단.** 별도 시험 기간을 두지 않는다. 운영자가 혼자 실제로 계속 쓰면서 발견한 문제를 고쳐 나가는 지속 개선 과정으로 보고, 범위 기능이 실제 사용 중 동작하는지로 판단한다(사용자 결정 2026-11-18, 2026-11-14의 '초대 지인 1~2명 사용 기록'과 2026-11-10의 '2주 매일 사용'을 대체). 초대 사용자의 사용 의견은 초대를 시작한 뒤의 개선 근거이며 완료 조건이 아니다. 문제의 근거: 운영자는 이 서비스의 전신인 개인 작업 공간(공고 관리·지원 추적 자동화)을 실제로 써 왔다(사용자 진술 2026-11-10). 전신 사용은 필요성의 근거이며 추천 품질의 검증을 대신하지 않는다. 이 프로젝트는 백엔드·홈서버 운영 학습을 함께 목표로 하는 개인 토이 프로젝트다.
- **데스크톱 상주 앱(사용자 결정 2026-11-18, 2026-11-14 제거 결정을 뒤집음).** 공고 찾기가 끝났을 때 브라우저를 열어 두지 않아도 알림을 받으려고 Electron 앱을 다시 둔다. macOS는 상단 메뉴 막대, Windows는 오른쪽 아래 알림 영역에 아이콘을 띄우고(메신저처럼), 창을 닫아도 앱은 아이콘으로 남아 서버 작업 결과를 OS 알림으로 알린다. 화면은 홈서버 웹을 그대로 쓰며 앱 안에 따로 만들지 않는다.
- **제외.** 공개 배포를 하지 않으므로 앱 스토어 배포·코드 서명·자동 업데이트, GA4·Discord는 범위에서 뺀다. 데스크톱 앱은 운영자가 직접 빌드해 자기 기기(Mac·Windows)에 설치한다. 최종 운영에서는 외부 AI(OpenAI 등)를 쓰지 않는다(구현 기간의 OpenAI 최소 사용은 예외).

이전 개정(2026-11-10)의 1차/2차 구분과 '아이디어' 표는 이 개정으로 대체한다. 단계 이름은 백로그의 작업 순서로만 남는다.

## 3. 사용자·범위

### 제공 조건

- 초대받은 소수의 취업·이직 준비자. 공개 가입·결제·스토어 출시는 하지 않는다.
- 직무: **프론트엔드·앱 개발·디자인·기획·백엔드·QA**(사용자 결정 2026-11-14). 앱 개발은 iOS·Android·크로스플랫폼, 디자인은 UI/UX·프로덕트 디자인, 기획은 서비스 기획·PM/PO, 백엔드는 서버·API 개발, QA는 소프트웨어 테스트·품질 보증(수동 테스트·테스트 자동화)이다. 희망 직무는 복수 선택한다. 직무를 더할 때는 직무별 정답 사례를 먼저 만든다.
- 공고 출처: **사람인·잡코리아·자소설닷컴·원티드·점핏**. 공개 수집 가능성·본문·지원 경로·마감 추출은 출처마다 검증하며 검증 전에는 지원한다고 표시하지 않는다. 점핏은 개발 직무 전용 플랫폼이므로 개발 직무(프론트엔드·앱 개발·백엔드·QA)를 고른 경우에만 조회하고, 디자인·기획은 나머지 네 출처에서 가져온다(사용자 결정 2026-11-14).
- 수집: 공개 페이지를 낮은 속도로 자동 수집한다. 공고는 갱신을 요청한 사용자의 자료로만 저장·판정하고 다른 사용자와 공유하지 않는다. 사용자가 공고 링크 한 건을 넣어 판정할 수도 있다. 로그인·차단 우회를 하지 않는다. 사람인은 OpenAPI가 승인되면 API로, 그 전에는 공개 페이지로 가져온다. 외부 허가 요청은 사람인 OpenAPI만 한다. 자소설닷컴·원티드는 약관상 사전 허락 없는 자동 수집을 금지하며, 운영자와 초대 사용자에게만 수집 결과를 제공하는 위험을 사용자가 인지하고 결정했다(근거는 기술 설계 D절).
- AI 처리: 최종적으로 홈서버의 로컬 LLM 하나로만 하고 이력서·공고·메일이 홈서버 밖 AI로 나가지 않는다. 구현 기간에는 사용자 본인 OpenAI 키로 공고 추출 위주로 최소한만 호출하며, 그동안은 외부 처리 사실을 안내한다(사용자 결정 2026-11-14). 로컬 LLM은 공고·서류·메일에서 구조화 정보를 뽑는 데만 쓰고, 추천 분류는 규칙이 정한다. 로컬 LLM이 확신하지 못한 항목은 미확인으로 두고 사용자가 판단한다. 사용자별 API 키 등록·모델 선택은 로컬 LLM으로 바꿀 때 제거한다.
- 판정 품질 기준: 추천 정답 사례에서 54/57 이상(gpt-5.5 수준, 사용자 결정 2026-11-14). 로컬 LLM 측정은 기능 구현 뒤 마지막에 한다. 기준에 못 미치면 기준을 낮추거나 모델·구조를 바꾸는 결정을 사용자에게 묻고, 임의로 완료 처리하지 않는다.
- 실제 수집이 불가능한 출처는 제약을 보고하고 범위 변경을 별도로 결정한다. 다른 출처로 임의로 바꾸거나 실패를 숨기지 않는다.
- 기업 규모·스타트업 여부는 공고·기업 소개에 명시된 정보가 있으면 출처와 함께 표시한다. 플랫폼 이름만으로 단정하지 않고 정보가 없으면 미확인이다. 별도 기업정보 수집 시스템은 두지 않는다.
- 메일: 네이버 계정을 연결한다. Gmail은 일단 범위에서 뺀다(사용자 결정 2026-11-14). 개인 키체인·회사별 예외·Notion 규칙을 서비스에 그대로 가져오지 않는다.
- 서류: 이력서 한 개(필수)와 포트폴리오·경력기술서(선택, 각 한 개)를 텍스트 PDF·MD·Notion ZIP·스캔 PDF로 등록한다. 모든 서류는 MD로 변환해 분석하며, 이미지가 있는 서류는 OCR로 MD를 만들고 사용자가 변환된 MD를 확인·수정할 수 있다(사용자 결정 2026-11-14). 새 문서 확인 성공 후 교체하며 실패하면 기존 문서를 유지한다. 추가 서류는 미등록이 기본값이다.

### 제공 기능

1. 초대 링크 가입·로그인·로그아웃과 사용자별 데이터 분리.
2. 네이버 연결 검사·연결 해제·재연결. 미연결 수동 이용 허용.
3. 이력서·포트폴리오·경력기술서 업로드(PDF·MD·Notion ZIP·스캔 PDF)·MD 변환 결과 확인·수정·교체·삭제.
4. 직무·관련 경력·지역·고용형태·업무/도구/기술 설정. 희망 직무 복수 선택.
5. 다섯 출처의 공고 수집·추천·근거·마감·마지막 확인 및 확인 가능한 기업 유형·규모 표시.
6. 고급 필터·선호·피드백, 도전/미확인 묶음 보기, 관심 없음·제외 복구.
7. 원문·지원 페이지를 기본 브라우저로 열기. 실제 제출은 사용자가 수행.
8. 지원 직접 등록·지원 현황 CSV 가져오기(엑셀·Notion 내보내기)·주요 상태 변경·검색·상태 필터·상세 근거.
9. 메일 증분 조회(1시간 주기)·조회 기간 선택·과거 범위 확장·대상 연결·상태 반영·열람 표시·누락 복구.
10. 모호·연결 불명·최종 결과 충돌을 확인 목록에서 연결·확정·무시·보류. 회사별 묶음 보기·연결 대상 제안·묶음 처리. 상태·필드 잠금.
11. 화면 안 갱신 결과·처리 중 건수와 남은 예상 시간·최근 성공·실패·다시 시도 표시.
12. 서버에서 하루 한 번 공고 갱신 예약 및 명시적 수동 갱신. 자동 ON/OFF.
13. 지원 건·문서·연결·계정 삭제 및 최소 이벤트·오류 기록.
14. 데스크톱 상주 앱: 메뉴 막대(macOS)·알림 영역(Windows) 아이콘, 창 닫기 후 상주, 로그인 시 자동 실행(켜고 끄기), 공고 갱신(수동·예약)이 끝나면 새 기본·도전 건수와 실패 여부를 OS 알림으로 알리고 알림을 누르면 추천 화면을 연다. 아이콘 메뉴: 열기·지금 공고 가져오기·마지막 결과·종료.

저장·연동·수집·로컬 LLM 처리가 실제로 작동해야 한다. 가상 데이터·목업 화면은 개발 중 시험 자료이며 완료 근거가 아니다.

## 4. 사용 흐름과 화면

초대 링크 가입 → 네이버 메일 연결 또는 건너뛰기 → 서류·필터 등록 → 추천 확인 → 외부 지원 → 접수 메일/사용자 확인 → 결과 갱신 → 확인 목록 처리.

- 최초 메일 조회는 최근 3개월을 기본값으로 안내하고 동의받는다. 기간 선택과 과거 범위 확장은 별도 작업으로 제공한다.
- 로컬 LLM 처리는 느리다(공고 1건 약 1분 추정, 실측 전). 수동 갱신도 백그라운드 작업으로 처리하고 화면은 처리 중 건수와 남은 예상 시간을 보여 준다.
- 서류·필터가 있어야 맞춤 추천한다. 메일 미연결이면 지원을 직접 등록·수정한다.

| 화면 | 내용 |
|---|---|
| 로그인 | 초대 링크 가입(이메일·비밀번호), 로그인·세션 만료·로그아웃 |
| 추천 | 목록·고급 필터·묶음(기본/도전/미확인)·공고 상세·추천 이유·미확인 조건·관심 없음·제외 복구·피드백·지원하기 |
| 지원 현황 | 상태별 목록·직접 등록·상세·직접 수정·잠금·근거 |
| 확인 목록 | 사용자 행동이 필요한 항목·연결·결과 확정·무시·보류 |
| 설정 | 메일 연결·서류·필터·자동 ON/OFF·조회 기간·삭제 |
| 갱신 결과 영역 | 처리중(건수·예상 시간)·성공·일부 실패·실패·최근 성공·재시도 |

같은 항목을 별도 페이지·모달·대시보드로 중복 구현하지 않는다.

화면 원칙(사용자 결정 2026-11-18, 디자인 시스템 재구축 기준). 강조색은 NextStep 인디고를 유지한다:

- 데스크톱 폭(데스크톱 앱 창 포함)을 기본으로 설계한다. 공통 틀은 왼쪽 아이콘 메뉴(추천·지원 현황·확인 목록·설정, 확인 목록은 대기 건수 표시), 페이지 머리(제목·한 줄 설명·요약 건수), 맨 아래 상태바다. 갱신 결과(마지막 갱신·처리 중 건수와 예상 시간·실패와 다시 시도)는 하단 상태바에 둔다. 좁은 창에서도 가로 스크롤 없이 쓸 수 있어야 한다.
- 추천과 지원 현황은 목록-상세 구조다. 목록은 두 줄 행에 판단에 필요한 것만(분류·제목·회사·마감·출처) 보여 주고, 근거(맞는 점·불충족·미확인)와 상태·변경 이력은 항목을 누르면 여는 상세 모달에서 본다. 긴 목록은 나눠 보여 주며 한 페이지에 전체를 펼치지 않는다. 확인 목록은 왼쪽 선택 항목 근거, 오른쪽 회사별 묶음 목록의 2분할이다.
- 키보드 단축키는 제공하지 않는다(사용자 결정 2026-11-18).
- 화면마다 주된 행동은 하나만 강조한다(추천: 새로 가져오기, 지원 현황: 직접 등록). 직접 등록·CSV 가져오기·공고 링크 판정처럼 가끔 쓰는 입력은 목록 위를 차지하지 않고 필요할 때 연다.
- 설정은 계정·메일·서류·프로필과 필터·자동 갱신으로 나눠 한 번에 한 구역만 보여 준다.
- 분류(기본·도전·미확인·제외)와 개인 상태(미지원~불합격)는 색만으로 구분하지 않고 글자와 함께 일관된 표시를 쓴다. 설명 문구는 짧게 두고 자세한 안내는 필요한 자리에서만 보여 준다.

## 5. 추천·상태·정정 원칙

### 추천

- 사용자가 확인한 프로필·필터와 공고의 명시 정보로 후보를 분류하고 맞는 이유·불충족·미확인을 표시한다.
- 사용자가 정하는 선호(직무·근무 지역·원격 포함·고용 형태·요구 경력 상한)는 모두 사용자가 고르는 공고 필터다. 서비스가 서류로 추정하거나 기본값을 넣지 않으며, 비어 있으면 제한하지 않는다. 필터는 공고 수집 요청과 추천 목록에 그대로 적용하고 화면에 현재 필터를 보여 준다(사용자 원칙 2026-11-08).
- 분류는 규칙으로 정한다(사용자 결정 2026-11-14): 로컬 LLM이 공고에서 직무·필수/우대 조건·요구 연차·고용 형태·포트폴리오 필수 여부를, 서류에서 보유 기술·직무별 연차를 뽑고, 규칙이 기본·도전·미확인·제외와 근거를 만든다. 같은 입력이면 같은 분류가 나와야 한다.
- 필수 조건이 명확히 불충족이면 기본 추천에서 제외한다. 최소 경력 부족은 도전, 필수 정보 불명은 미확인으로 구분한다.
- 우대 일치는 순서에 반영하되 우대 부족만으로 제외하지 않는다. 점수·합격 확률은 제공하지 않는다. 피드백은 그 사용자의 추천 순서·숨김에만 쓰고 곧바로 회사·직무 전체 차단으로 해석하지 않는다.
- 서류 미기재와 경험 부족, 총 경력과 직무 경력, 동의어와 유사 기술을 구분한다. 확인할 수 없으면 미확인으로 둔다.
- 직무마다 직무 분류·관련 경력·필수/우대 조건 사례로 추천을 검증한다. 개발 기술만으로 디자인·기획 적합성을 평가하지 않고, QA는 테스트 설계·자동화 도구·품질 업무 경험으로 평가한다.
- 관심 없음은 해당 공고 숨김과 해제를 제공한다.

### 개인 상태와 공고 상태

| 개인 상태 | 의미 |
|---|---|
| 미지원 | 추천·저장 또는 사용자 미지원 확인 |
| 지원 완료 | 명확한 접수 메일 또는 사용자 확인 |
| 전형 진행중 | 서류 통과·과제·면접 안내 |
| 합격 | 명확한 최종 합격 또는 사용자 확인 |
| 불합격 | 명확한 서류·면접 불합격 또는 사용자 확인 |

- 열람은 별도 속성. 미열람과 열람 정보 없음을 구분한다.
- 공고는 모집중·마감·미확인으로 별도 관리한다. 공고 종료만으로 개인 상태를 불합격으로 바꾸지 않는다.
- 확인된 마감 정보로 모집 상태를 표시한다. 근거가 없으면 임의 종료하지 않고 최근 확인 시각을 보여준다.
- 지원하기 클릭만으로 지원 완료를 만들지 않는다. 같은 회사의 다른 직무·재지원 회차는 별도 지원이다.
- 메일만으로 모든 플랫폼 상태를 알 수 있다고 약속하지 않는다.

### 메일·확인·정정

- 공고/접수 식별자 → URL → 회사+직무+회차·시간 관계 순으로 연결한다. 회사명만 같거나 후보가 하나뿐이라는 이유로 확정하지 않는다.
- 접수 없이 결과만 있어도 회사·직무·결과가 명확하면 지원 건을 만들 수 있다. 실제 지원일은 미확인으로 남긴다.
- 회사 없는 메일·홍보는 상태 반영에서 제외한다. 결과가 불명확하면 모호로 둔다.
- 확인 목록은 연결·결과 확정·무시·보류를 제공한다. 반복 모달로 재촉하지 않고 같은 근거는 재요청하지 않는다.
- 확인 목록은 메일에서 읽은 회사별로 묶고, 같은 회사 지원 건이 하나뿐이면 연결 대상으로 제안한다. 제안은 자동 확정하지 않으며 사용자가 한 건 또는 묶음으로 확정한다(사용자 결정 2026-11-15).
- 지원 현황 CSV 가져오기(회사·직무·상태, 선택 공고 URL)는 같은 회사·직무를 중복 등록하지 않고, 대기 중인 연결 불명 메일을 가져온 지원 건으로 다시 연결해 본다. 파일 원문은 보관하지 않는다(사용자 결정 2026-11-15).
- 잘못된 판정·연결을 정정하면 그 근거의 재적용을 막는다. 새 독립 근거는 재평가한다. 사용자가 잠근 상태·필드는 메일로 바꾸지 않는다.
- 오래된 접수·열람은 최신 결과를 되돌리지 않는다. 최종 결과 충돌·최신성 불명은 현재 값을 유지하고 확인받는다.

## 6. 자동 실행·권한·운영

- 홈서버에서 하루 한 번 공고 수집 → 추천 갱신을 실행한다(초기 21시). 메일은 1시간 주기로 증분 조회한다.
- 로컬 LLM 처리에는 하루 처리 상한을 두고, 남은 건은 다음 실행으로 넘기며 화면에 표시한다. 모델 호출은 한 번에 하나다.
- 수동 메일 조회·공고 가져오기·추천 재계산은 작업 종류를 구분하고, 같은 종류 중복 요청은 진행 작업에 합류시킨다.
- 공고는 사용자별 갱신으로 수집해 그 사용자 자료로만 저장하고 각자의 프로필로 추천한다. 브라우저·사용자 컴퓨터 화면을 자동 조작하지 않는다.
- 앱 종료·사용자 컴퓨터 꺼짐 상태에서도 홈서버 작업이 실행된다. 홈서버는 재부팅 후 자동 시작하고 Tailscale 사설망으로만 접속하며 외부 포트를 열지 않는다. 로컬 LLM은 홈서버 안에서만 접근한다.
- 초대 계정에는 자동화 권한을 부여한다. 자동 OFF·연결 해제·권한 회수 시 새 예약 작업은 실행하지 않는다. 진행 중 자동 작업은 반영 직전 권한을 다시 확인한다.
- 화면에는 갱신 결과·최근 성공·적용·확인 요청·실패 건수를 표시한다. 브라우저를 닫아도 서버 자동화는 계속된다.
- 데스크톱 상주 앱은 서버 작업을 직접 실행하지 않고 서버의 갱신 결과를 확인해 알린다. 같은 결과를 두 번 알리지 않고, 앱이 꺼져 있던 동안 끝난 갱신은 다음 실행 때 한 번만 알린다. 알림에는 건수와 성공·실패만 넣고 공고 원문·이력서 내용은 넣지 않는다.
- 백업(DB·서류 파일·비밀 키)은 홈서버 노트북 밖(운영자 Mac·외장 디스크 등)에 두고 복구를 연습한다. 같은 노트북의 다른 디스크만으로는 백업으로 보지 않는다. 작업 실패·디스크·로그 확인 방법을 운영 범위에 포함한다.

## 7. 범위 밖과 재검증 후보

- 공개 배포·랜딩 페이지·공개 가입·결제: 하지 않는다(2026-11-10). 수집한 공고를 불특정 다수에게 제공하면 자소설닷컴·원티드 약관과 채용공고 크롤링 판례에 정면으로 걸린다.
- 앱 배포·서명·자동 업데이트, GA4·Discord·운영 대시보드: 공개 배포가 없어 제외(2026-11-14).
- 외부 AI 처리(OpenAI·본인 GPT·Claude 계정 연결): 제외(2026-11-14). 로컬 LLM이 품질 기준을 못 넘을 때 다시 검토할지는 사용자가 정한다.
- Gmail: 일단 제외(2026-11-14). 다시 넣을 때 연결 방식(OAuth / IMAP+앱 비밀번호)을 정한다.
- 마케팅 직무: 제외(2026-11-14).
- 필요성을 다시 검증할 기능: Linux 데스크톱, HWP/HWPX, 자기소개서 별도 종류, 문서 버전 복구·실제 제출본 보관, Excel·Notion 직접 연동(CSV 가져오기는 포함), 상세 일정 캘린더·예약 알림. 자동 지원·메일 발송은 범위에서 제외한다.

## 8. 미룰 수 없는 보호와 완료 조건

- 사용자 인증·데이터 격리·비공개 파일 접근·비밀정보 보호·연결 해제·데이터 삭제를 제공한다.
- 메일 읽음·삭제·이동·회신을 하지 않는다. 일반 메일 원문·연락처·인증정보를 로그·분석·프로젝트 파일에 저장하지 않는다.
- 최종 AI 처리는 홈서버 로컬 LLM에서만 하고 그 사실을 안내한다. 구현 기간 OpenAI 사용 중에는 외부 전달 범위를 안내한다. 불명확한 결과를 자동 확정하지 않는다.
- 외부 링크(원문·지원 페이지)는 URL·스킴을 검사해 새 창으로 연다. 세션을 검증한다.
- 지원 ID·출처·메시지 ID·정정 근거를 유지해 범위가 늘어도 기존 사용 기록을 버리지 않는다.

### 완료 조건

1. 사설망으로 홈서버에 접속해 로그인하고 서류·필터·지원 건을 저장한 뒤 다시 접속해 확인한다.
2. 다섯 출처의 실제 공고를 자동 수집해 추천 이유·마감·지원 링크를 제공한다. 공고는 갱신한 사용자 자료로만 저장되고 AI 처리는 홈서버 로컬 LLM으로만 한다. 여섯 직무(프론트엔드·앱 개발·디자인·기획·백엔드·QA) 각각을 검증하며 수집 실패는 드러나야 한다. 기업 유형·규모 미확인은 사실처럼 채우지 않는다.
3. 추천 정답 사례(직무별 사례 포함)에서 로컬 LLM 경로가 54/57 이상을 낸다. 추가 직무 사례도 같은 방식으로 측정해 기록한다.
4. 포트폴리오·경력기술서·Notion ZIP·스캔 PDF를 등록하면 MD로 변환되고(이미지는 OCR), 사용자가 MD를 확인·수정·교체·삭제할 수 있으며, 실패 시 기존 문서를 유지하고 추천에 반영된다.
5. 네이버 연결과 초기 조회·1시간 증분 조회·기간 선택·과거 범위 확장·재연결이 실제로 작동하고 같은 메일을 반복 처리해도 중복되지 않는다.
6. 접수 → 전형 진행중 → 최종 결과와 열람이 정책대로 반영되고 모호한 결과는 확인 목록에서 해결된다. 잠금한 상태·필드는 메일로 바뀌지 않는다.
7. 같은 회사 다른 직무·결과만 있는 메일·URL 없는 메일·회사 없는 메일·오래된 메일·정정 재처리를 검증한다.
8. 사용자 컴퓨터·브라우저를 끈 동안 홈서버 예약 작업이 처리되고 다음 접속에서 결과가 보인다. 홈서버 재부팅 후 자동 시작하고, 노트북 밖에 둔 백업으로 다른 위치에 복구해 로그인·자료를 확인하며, 사설망 밖에서는 접속할 수 없다. 초대 사용자가 Tailscale 공유로 접속한다.
9. 공고 마감은 개인 불합격으로 바뀌지 않으며 회사·직무 오연결·근거 없는 최종 결과·데이터 혼합이 필수 사례에서 발생하지 않는다.
10. 파일 실패 시 기존 서류 유지, 사용자별 접근 차단, 연결·서류·지원·계정 삭제, 오류 재시도가 동작한다.
11. 운영자가 혼자 실제로 계속 쓰면서 발견한 오류의 재현·수정 여부를 검증 기록에 남긴다. 별도 시험 기간과 초대 지인 사용 기록은 완료 조건에 두지 않는다(2026-11-18).
12. 데스크톱 상주 앱이 macOS 메뉴 막대·Windows 알림 영역에 아이콘으로 상주하고, 창을 닫아도 남아 있으며, 예약·수동 공고 갱신이 끝나면 OS 알림이 한 번 오고 알림을 누르면 추천 화면이 열린다. 앱이 꺼져 있어도 서버 작업은 계속되고 다음 실행 때 놓친 결과를 한 번 알린다.
13. 네 화면(추천·지원 현황·확인 목록·설정)과 로그인이 디자인 시스템의 토큰·공통 컴포넌트만으로 구성되고(화면 안 임의 색·크기 없음), 화면 원칙(하단 상태바의 갱신 결과, 목록과 상세 모달, 주된 행동 하나, 긴 목록 나눔, 설정 구역 분리)을 따른다. 1440px·1024px 폭과 Light/Dark에서 Storybook과 실제 화면 캡처로 확인한다.

정답 표본의 연결 정확도·상태 판정·누락을 분리 측정한다. 특정 사례 통과를 전체 무오류 보장으로 표현하지 않는다.

## 9. 문서의 우선순위와 남은 결정

이 문서의 범위가 과거 대화·이전 개정의 1차/2차 표기보다 우선한다. 화면의 현재 사실은 구현(`apps/web`)이 가진다. 남은 결정과 그것이 막는 단계는 [백로그의 미결 결정](백로그.md#미결-결정)이 소유한다. 데이터 구조·로컬 LLM 처리·확장 설계는 [기술 설계](기술설계.md), 구현 순서와 현재 상태는 [백로그](백로그.md)를 따른다.
